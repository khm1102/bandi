# bandi 목업 운영·UX 검토 기록

> 문서 상태: 1차 구현 참고 자료
> 작성 기준일: 2026-07-18
> 검토 기준: 확정된 기능 기획, 실제 JSP·JavaScript, 375px·768px·1280px 화면 캡처
> 관련 문서: `feature-spec.md`, `member-onboarding-plan.md`, `performance-operations-plan.md`
> 범위 주의: 온보딩 관련 화면 제안은 후속 참고안이며 1차 구현 범위가 아니다.

## 1. 결론

현재 목업은 내부 관리 화면의 시각적 방향과 공통 컴포넌트를 확인하는 용도로는 쓸 수 있다. 그러나 그대로 기능 구현의 기준으로 사용하기에는 확정된 기획과 다른 화면이 많고, 실제 운영에 필요한 작성·검수·게시·보관 흐름이 부족하다.

우선순위는 다음과 같다.

1. 학교 SSO, 메뉴 구조, 권한과 같은 확정 기획을 목업에 먼저 동기화한다.
2. 모바일 가로 잘림과 핵심 업무 접근 불가 문제를 해결한다.
3. 모든 업무를 목록과 간단한 모달로 끝내지 않고, 중요도와 작성 복잡도에 따라 상세·작성 페이지를 제공한다.
4. 공개 공연 페이지, 관람 정책, 문의와 개인정보 안내를 포함한 실제 외부 운영 흐름을 완성한다.
5. 빈 상태, 오류, 권한 거부, 임시 저장, 게시 종료와 같은 운영 상태를 화면에 포함한다.

따라서 다음 구현 단계에서는 현재 화면을 그대로 다듬기보다 정보 구조와 화면 목록을 먼저 확정한 뒤, 공통 셸은 유지하면서 각 기능을 교체하는 편이 안전하다.

## 2. 검토 범위와 근거

### 2.1 확인한 대표 화면

- 로그인
- 홈
- 자료실
- 활동 기록
- 커뮤니티 게시판
- 공연 체크리스트
- 멤버·권한
- 관람 신청

홈은 1280px, 768px, 375px에서 비교했고 로그인·자료실·관람 신청은 모바일 화면을 추가로 확인했다.

### 2.2 현재 목업에서 유지할 기반

- 공개 화면, 인증 화면, 내부 화면을 서로 다른 셸로 나눈 방향
- 모달의 초점 이동, `Escape` 닫기와 닫힌 뒤 초점 복원
- 키보드 초점 표시
- 표의 가로 스크롤 기본 처리
- 이미지 크기 명시로 인한 레이아웃 이동 방지
- 공통 버튼, 필터, 표와 카드 태그를 사용하려는 구조

이 기반은 유지하되 기능 의미와 운영 흐름을 새 기획에 맞게 바꾼다.

## 3. 우선순위별 발견 사항

### 3.1 치명적 문제

| 항목 | Before | After | Why |
|---|---|---|---|
| 로그인 모델 불일치 | 아이디·비밀번호 로그인, 회원가입 탭, 초대코드 가입을 제공한다. | 학교 SSO 로그인 하나만 제공하고, 미등록·휴학·졸업·학교 장애 상태를 각각 안내한다. | 수동 사전 등록과 재학생 SSO라는 확정 운영 정책과 정면으로 충돌한다. |
| 폐기 기능 잔존 | 일정 조율과 커뮤니티 게시판이 메뉴, 라우트, 홈 바로가기에 남아 있다. | 일정 조율과 커뮤니티를 제거하고 공시, 공지·자료실, 활동 기록을 명확히 분리한다. | 사용자가 폐기된 기능에 데이터를 쌓기 시작하면 이후 마이그레이션과 안내 비용이 커진다. |
| 모바일 가로 잘림 | 375px에서 로그인 탭, 홈 카드·역할 전환기, 자료실 검색·버튼·표가 화면 밖으로 잘린다. | 작은 화면에서 역할 전환기를 접거나 숨기고, 헤더 행동을 세로 배치하며, 카드 1열과 `min-width: 0` 규칙을 적용한다. | 모바일에서 로그인과 핵심 업무가 불가능하거나 일부 행동을 발견할 수 없다. |
| 모달 중심 작성 | 공지, 활동 기록과 주요 생성 작업이 짧은 모달 입력으로 끝난다. | 짧고 되돌리기 쉬운 작업만 모달에 두고, 중요하거나 긴 글은 작성·미리보기·게시가 분리된 전용 페이지로 이동한다. | 장문, 첨부, 공개 범위, 검수, 임시 저장과 수정 이력을 안정적으로 처리할 수 없다. |

### 3.2 운영 영향이 큰 문제

| 항목 | Before | After | Why |
|---|---|---|---|
| 활동 기록 증빙 부족 | 날짜, 참여 인원과 짧은 내용만 입력하며 사진 첨부와 검수 상태가 없다. 일반 부원의 작성 버튼도 숨겨져 있다. | 활동 기록 전용 작성 페이지에서 참여자, 사람과 네이비즘 화면이 함께 나온 인증 사진, 추가 사진, 제출 상태를 관리한다. 일반 부원은 소속 팀 기록을 작성할 수 있다. | 활동 기록의 목적 자체가 네이비즘 인증이므로 현재 모달로는 핵심 업무를 수행할 수 없다. |
| 공지와 자료의 혼합 | 자료실에서 `공지 작성`과 파일 업로드를 함께 제공하고, 중요 공지를 PDF 한 행처럼 표시한다. | 하나의 정보 허브 안에서 `공지`와 `자료` 탭을 제공하되 데이터, 작성 화면, 권한과 상태는 분리한다. | 공지는 읽음 확인·게시 상태가 중요하고 자료는 파일 버전·분류가 중요하다. 같은 레코드로 다루면 운영 기준이 흐려진다. |
| 공시 화면 부재 | 기존 커뮤니티가 자유글·질문·좋아요·댓글 중심이다. | 외부 공개 공시 목록·상세와 운영진의 공시 작성·예약 게시·게시 종료 화면을 제공한다. | 공시는 대외 공식 정보이며 커뮤니티 글과 공개 책임, 보존 정책이 다르다. |
| 멤버 등록 방식 불일치 | 초대코드를 만들고 사용자가 직접 가입하는 흐름이다. | 운영진이 학번, 이름, 기수, 팀을 사전 등록하고 SSO 연결 대기·활성 상태를 관리한다. 온보딩 진행 상태는 후속 기능에서 추가한다. | 확정된 모집 B안과 맞지 않으며, 한 사람 한 팀 정책과 학적 검증을 보장하기 어렵다. |
| 공개 공연 정보 부족 | 관람 신청 화면에 포스터, 작품 요약, 좌석과 신청 폼만 있다. | 별도 공연 홍보 페이지에 시놉시스, 캐스팅 보드, 제작진, 회차, 관람·입장·취소·접근성 정책, 장소, 문의와 공시를 제공한다. | 외부 관람객은 신청 전에 공연과 운영 정책을 충분히 판단할 수 있어야 한다. |
| 신청 후 여정 부족 | 좌석 신청이 주 흐름의 끝이며 조회·취소·QR 입장 안내가 연결되지 않는다. | 신청 완료에서 조회 토큰·QR·취소 마감·입장 안내로 이어지고, 공개 헤더에서 신청 조회에 접근할 수 있게 한다. | 현장 문의, 중복 신청과 취소 요청을 운영진이 수작업으로 처리하게 된다. |
| 상세 화면 부족 | 많은 기능이 목록 카드와 즉시 상태 변경만 제공한다. | 공지, 자료, 활동 기록, 행사, 공연 프로젝트, 장비에는 상세 화면과 변경 이력을 제공한다. | 작성 맥락과 이전 상태를 확인하지 못한 채 수정·삭제하면 운영 사고가 발생한다. |
| 프로젝트 범위 부족 | 체크리스트와 제작 상태가 어느 학기 공연인지 화면에서 명확하지 않다. | 모든 제작 업무, 소품 사용과 체크리스트 상단에 현재 공연 프로젝트와 회차 범위를 표시하고 전환할 수 있게 한다. | 학기당 공연 하나라는 기준을 화면에서도 강제해야 지난 공연 데이터 오염을 막을 수 있다. |
| 행사·출석 운영 정보 부족 | 행사 카드와 단순 출석 처리가 중심이다. | 대상 멤버, 출석 가능 시간, 상태, 수동 정정 사유, 처리자와 처리 이력을 제공한다. | 실제 출석은 사후 정정과 이의 확인이 빈번하므로 단순 토글만으로 운영하기 어렵다. |
| 운영 상태 화면 부재 | 정상 데이터가 있는 상태만 주로 표현한다. | 로딩, 빈 상태, 검색 결과 없음, 저장 실패, 권한 없음, 만료, 보관, 외부 시스템 장애를 화면별로 정의한다. | 실제 서비스에서 가장 많은 문의는 정상 흐름 밖의 상태에서 발생한다. |

### 3.3 빠르게 개선할 항목

| 항목 | Before | After | Why |
|---|---|---|---|
| 개발 역할 전환기 | 모바일 본문 폭을 차지하며 실제 기능처럼 보인다. | 개발 프로필에서만 노출하고 모바일에서는 한 개의 메뉴로 접는다. 운영 배포에서는 제거한다. | 사용자 혼란과 가로 넘침을 동시에 줄인다. |
| 터치 영역 | 일부 필터 칩과 작은 버튼 높이가 32~36px다. | 모바일에서는 핵심 조작의 최소 높이를 44px로 맞춘다. | 작은 화면에서 오조작을 줄인다. |
| 모션 감축 | 토스트와 전환 효과가 있으나 `prefers-reduced-motion` 대응이 없다. | 감축 설정에서는 이동 애니메이션을 제거하거나 즉시 전환한다. | 멀미와 주의 분산을 줄이고 접근성을 높인다. |
| 런타임 스타일 의존 | 브라우저에서 외부 Tailwind 스크립트를 받아 스타일을 생성한다. | 배포 빌드에서는 CSS를 미리 생성해 자체 정적 자원으로 제공한다. | 외부 CDN 장애, CSP, 초기 렌더링과 운영 안정성 문제를 줄인다. |
| 목록 탐색 | 검색·필터는 있으나 페이지 이동, 정렬 상태와 URL 보존 기준이 불명확하다. | 검색, 필터, 정렬, 페이지를 URL에 보존하고 결과 수와 초기화 기능을 제공한다. | 새로고침·뒤로 가기·링크 공유에서 업무 맥락을 유지할 수 있다. |

## 4. 권장 정보 구조

### 4.1 내부 서비스

```text
홈
통합 캘린더
공지·자료실
├── 공지
└── 자료
활동 기록
행사·출석
회비
공연 제작
├── 팀별 제작 진행
├── 소품·장비
├── 공연 체크리스트
├── 관람 신청 관리
└── 입장 관리
멤버 관리
├── 멤버·권한
└── 사전 등록·SSO 연결
[후속] 온보딩 관리
공시 관리 (운영진 전용)
```

- 일정 조율과 커뮤니티는 제거한다.
- 공시는 외부 공개 정보이므로 공개 사이트의 `공시`와 운영진 전용 `공시 관리`를 연결한다.
- 공지와 공시는 둘 다 유지하되, 공지는 내부 구성원 대상이고 공시는 외부 공개 대상이라는 차이를 메뉴명과 작성 화면에서 반복해서 보여준다.

### 4.2 외부 서비스

```text
공연 소개
├── 작품·시놉시스
├── 캐스팅 보드
├── 제작진·미디어
├── 회차·관람 안내
└── 장소·문의
공시
관람 신청
신청 조회·취소
멤버 로그인
```

공개 공연 페이지가 관람 신청의 상위 화면이 되고, 현재 관람 신청 폼은 그 안에서 선택한 회차와 좌석을 확정하는 단계로 사용한다.

## 5. 모달과 전용 페이지 사용 기준

### 5.1 판단 원칙

다음 조건을 모두 만족하면 모달을 사용한다.

- 한 가지 목적의 짧은 작업이다.
- 입력 항목이 대략 5개 이하이고 장문 작성이 없다.
- 첨부파일 미리보기나 복잡한 검증이 없다.
- 임시 저장, 버전, 승인이나 공개 미리보기가 필요하지 않다.
- 작업 실패 후 쉽게 다시 시도하거나 되돌릴 수 있다.

다음 중 하나라도 해당하면 전용 작성·수정 페이지를 사용한다.

- 외부 또는 전체 멤버에게 게시되는 중요한 글이다.
- 장문, 여러 첨부파일, 이미지 순서 또는 미리보기가 필요하다.
- 임시 저장, 예약 게시, 검수, 승인, 수정 이력이 필요하다.
- 대상, 권한, 상태와 공개 기간을 함께 결정한다.
- 작성 중 다른 자료나 화면을 참고해야 한다.

### 5.2 기능별 권장 방식

| 기능 | 권장 UI | 이유 |
|---|---|---|
| 짧은 일정 추가 | 모달 | 제목, 일시, 장소와 팀을 빠르게 입력한다. 반복·상세 일정은 페이지 확장을 검토한다. |
| 체크리스트 항목 추가 | 모달 | 한 문장 항목, 담당 팀, 필수 여부와 회차만 선택한다. |
| 출석 상태 정정 | 확인 모달 | 상태, 사유와 확인만 필요하며 감사 이력을 남긴다. |
| 멤버 사전 등록 | 모달 또는 짧은 페이지 | 단건은 모달, 여러 명 등록·검증 결과 확인은 전용 페이지가 낫다. |
| 공시 작성 | 전용 페이지 | 공식 공개, 임시 저장, 미리보기, 공개 기간과 수정 이력이 필요하다. |
| 중요·장문 공지 | 전용 페이지 | 대상 범위, 첨부, 읽음 확인과 예약 게시가 필요하다. |
| 짧은 공지 | 빠른 작성 모달 + `상세 작성` 이동 | 제목과 짧은 본문만 빠르게 쓰되 중요 설정이 생기면 페이지로 전환한다. |
| 자료 업로드 | 모달 | 파일과 짧은 메타데이터만 입력한다. 여러 버전·상세 설명은 상세 페이지에서 관리한다. |
| 활동 기록 | 전용 페이지 | 참여자, 인증 사진, 추가 사진, 설명, 제출과 보완 요청을 함께 다룬다. |
| 온보딩 템플릿 | 후속 전용 편집 페이지 | 단계 순서, 유형, 필수 여부, 팀·기수 적용과 미리보기가 필요하다. 1차 구현에서는 만들지 않는다. |
| 공연 홍보 콘텐츠 | 전용 편집 페이지 | 섹션이 많고 외부 공개 미리보기와 게시 상태가 필요하다. |
| 팀별 제작 업무 | 모달 + 상세 패널 | 빠른 생성은 모달로 하고 설명·이력·차단 사유는 상세에서 관리한다. |

### 5.3 장문 작성 페이지 공통 구조

```text
상단: 뒤로 가기 / 작성 상태 / 임시 저장 시각
본문: 제목 / 대상·분류 / 본문 편집 / 첨부
보조 영역: 게시 설정 / 중요 여부 / 공개 기간 / 권한
하단: 취소 / 미리보기 / 임시 저장 / 게시 또는 제출
```

공통 동작은 다음과 같다.

- 자동 또는 수동 임시 저장과 마지막 저장 시각
- 저장하지 않은 변경이 있을 때 이탈 경고
- 파일 업로드 진행률, 실패 재시도와 삭제
- 모바일 미리보기와 실제 공개 화면 미리보기
- `임시 저장`과 `게시·제출`의 명확한 분리
- 게시 후 수정자, 수정 시각과 버전 이력
- 검증 오류 발생 시 첫 오류로 초점 이동

## 6. 글과 콘텐츠의 운영 수명주기

목록·작성 화면만 만들지 않고 기능별 상태 전이를 먼저 정의한다.

| 콘텐츠 | 권장 상태 | 주요 운영 행동 |
|---|---|---|
| 공시 | 임시 저장 → 공개 예정 → 게시 중 → 게시 종료 → 보관 | 미리보기, 예약 게시, 긴급 수정, 종료, 변경 이력 |
| 공지 | 임시 저장 → 게시 중 → 게시 종료 → 보관 | 대상 지정, 중요 고정, 읽음·미확인 확인, 재공지 |
| 자료 | 임시 저장 → 게시 중 → 교체됨 → 보관 | 파일 검증, 버전 교체, 이전 버전 확인 |
| 활동 기록 | 작성 중 → 제출 → 승인 또는 보완 요청 → 보관 | 증빙 검수, 보완 의견, 재제출, 수정 이력 |
| 행사 | 예정 → 출석 처리 중 → 종료 → 정정 가능 → 마감 | 대상 확정, 현장 처리, 수동 정정, 이력 확인 |
| 공연 페이지 | 작성 중 → 공개 예정 → 공개 → 공연 종료 → 보관 | 미리보기, 회차·공시 연결, 종료 후 기록 유지 |

물리 삭제는 명백한 오등록과 게시 전 초안에 제한하고, 운영 기록은 게시 종료 또는 보관 상태로 남기는 방향을 기본으로 한다.

## 7. 푸터 운영 정책

푸터는 모든 화면에 큰 영역으로 반복하기보다 화면 셸별 책임을 다르게 둔다.

### 7.1 공개 화면 푸터

공연 홍보, 공시, 관람 신청과 신청 조회 화면에는 다음 정보를 제공한다.

- 운영 주체 또는 동아리명
- 대표 문의 수단과 응답 가능 시간
- 개인정보 처리 안내
- 관람 신청·취소 정책
- 입장·지연 입장·촬영·접근성 안내
- 공연장 주소와 오시는 길
- 공식 SNS 또는 외부 채널
- 저작권, 포스터·사진 크레딧

공연별로 달라지는 정보는 공연 콘텐츠에서 관리하고, 개인정보·서비스 정책처럼 공통인 정보는 공통 페이지로 연결한다.

### 7.2 로그인·인증 화면 푸터

- 학교 계정 비밀번호를 저장하지 않는다는 짧은 안내
- 로그인 장애와 멤버 미등록 문의 경로
- 개인정보 처리 안내
- 서비스 운영 주체

### 7.3 내부 화면 하단 정보

내부 관리 화면마다 큰 푸터를 넣을 필요는 없다. 사이드바 하단 또는 사용자 메뉴에 다음 항목을 간결하게 둔다.

- 도움말·운영 문의
- 개인정보 처리 안내
- 서비스 버전 또는 배포 시각
- 장애 공지 또는 상태 페이지 링크

현재 `© bandi`만 있는 공개 푸터는 실제 관람 운영에 필요한 책임과 문의 정보를 제공하지 못하므로 교체 대상이다.

## 8. 화면별 변경안

### 8.1 로그인

- 회원가입 탭과 초대코드를 제거한다.
- 학교 SSO 로그인 행동을 하나만 제공한다.
- 재학생만 사용할 수 있다는 조건과 학교 비밀번호 비저장 안내를 표시한다.
- 학교 장애, 인증 실패, 멤버 미등록, SSO 연결 대기, 학적 제한을 서로 다른 오류 화면으로 제공한다.
- 관람객 신청은 내부 로그인과 분리된 공개 헤더에서 계속 접근할 수 있게 한다.

### 8.2 홈

- 최근 게시판을 중요 공지와 미확인 공지로 교체한다.
- 일정 조율 바로가기를 제거한다.
- 역할별로 `지금 처리할 일`을 먼저 보여준다.
- 일반 부원은 미확인 공지, 가까운 일정, 출석과 회비를 우선한다.
- 팀장은 활동 기록 보완 요청, 팀 일정과 제작 차단 업무를 우선한다.
- 운영진은 멤버 연결 대기, 미확인 중요 공지, 출석 미처리와 회비 미납 집계를 우선한다.
- 모바일에서는 카드 1열과 핵심 행동의 세로 배치를 사용한다.

### 8.3 공지·자료실

- 허브 첫 화면에 `공지`와 `자료`를 명확한 탭으로 분리한다.
- 공지는 읽은 사람·미확인 사람, 중요 여부, 게시 상태와 대상 범위를 표시한다.
- 자료는 파일명보다 자료 제목을 중심으로 하고 분류, 버전, 업로더와 교체 이력을 제공한다.
- 공지 상세와 자료 상세를 각각 제공한다.
- 모바일 표는 핵심 정보 카드 또는 우선 열을 제공하고, 전체 정보는 가로 스크롤로 보조한다.

### 8.4 활동 기록

- 목록에 팀, 활동 일시, 참여자, 대표 인증 사진, 검수 상태와 보완 여부를 표시한다.
- 일반 부원에게 소속 팀 기록 작성 기능을 제공한다.
- 전용 작성 페이지에서 참여자와 네이비즘 화면이 함께 보이는 사진을 필수로 받는다.
- 운영진의 보완 요청과 작성자의 재제출 흐름을 제공한다.

### 8.5 행사·출석

- 참석 의사 투표 UI를 만들지 않는다.
- 행사 대상, 출석 확인 가능 시간과 현재 상태를 표시한다.
- 운영진·팀장은 출석 정정 사유와 처리 이력을 확인한다.
- 행사 종료 후 미처리 인원과 출석 통계를 확인하고 마감한다.

### 8.6 멤버·후속 온보딩

- 초대코드 영역을 사전 등록과 SSO 연결 현황으로 교체한다.
- 1차 구현에서는 학번, 이름, 한 개의 팀, 기수, 역할, 학적 확인 결과, 멤버 상태와 SSO 연결 상태를 구분한다.
- 상태별 필터와 일괄 안내 대상을 제공하되 권한 변경은 개별 확인을 거친다.
- 온보딩 템플릿과 진행 상태는 후속 구현에서 별도 편집 화면과 멤버 미리보기로 제공한다.

### 8.7 공연 제작·관람

- 내부 제작 화면에 현재 학년도·학기 공연 프로젝트를 항상 표시한다.
- 공개 공연 페이지에서 관람 신청으로 진입하게 한다.
- 신청 완료 후 신청 조회·취소·QR 입장 안내를 제공한다.
- 현장 입장 화면은 QR 스캔을 기본으로 하고 이름·연락처 검색을 장애 대응 수단으로 둔다.
- 푸터와 관람 안내에서 취소 마감, 지연 입장, 촬영, 접근성과 문의 정보를 반복 확인할 수 있게 한다.

## 9. 공통 운영 상태

모든 주요 화면은 다음 상태를 정의해야 한다.

- 최초 데이터 없음
- 검색·필터 결과 없음
- 로딩 중
- 저장·업로드 중
- 일부 데이터만 불러옴
- 저장 실패와 재시도
- 권한 없음
- 로그인 또는 조회 토큰 만료
- 보관되거나 게시 종료된 데이터
- 외부 학교 시스템 또는 파일 저장소 장애

오류 화면에는 실패 사실뿐 아니라 사용자가 할 수 있는 다음 행동, 데이터 보존 여부와 문의 경로를 함께 표시한다.

## 11. 1차 화면 개편 완료 조건

- 375px에서 로그인, 홈, 공지·자료실과 관람 신청에 가로 스크롤이나 잘린 핵심 행동이 없다.
- 폐기한 일정 조율과 커뮤니티가 메뉴, 홈, 라우트와 화면 문구에 남지 않는다.
- 로그인 화면에 로컬 회원가입이나 초대코드가 없고 학교 SSO 예외 상태를 구분한다.
- 공시, 공지, 자료와 활동 기록의 목록·상세·작성 책임이 구분된다.
- 활동 기록에서 인증 사진 제출과 운영진 보완 요청이 가능하다.
- 중요 콘텐츠는 임시 저장, 미리보기, 게시·제출과 이탈 경고를 제공한다.
- 멤버 화면에서 사전 등록, SSO 연결, 단일 팀과 활동 상태를 확인할 수 있다.
- 공개 공연 화면에서 작품 정보, 캐스팅, 회차, 관람 정책, 문의, 신청 조회·취소로 이동할 수 있다.
- 푸터 또는 내부 도움말 영역에서 운영 주체, 문의와 개인정보 안내에 접근할 수 있다.
- 정상, 빈 상태, 오류, 권한 없음과 만료 상태가 정의돼 있다.

## 12. 추가 확정이 필요한 사항

1. 공시 관리를 운영진 사이드바의 독립 메뉴로 둘지 공연 제작 안에 둘지 결정한다.
2. 짧은 공지의 빠른 작성 모달을 유지할지 모든 공지를 전용 페이지에서 작성할지 결정한다.
3. 공지 본문 편집기를 일반 텍스트, 제한된 서식 또는 Markdown 중 무엇으로 제공할지 결정한다.
4. 자료 파일의 이전 버전을 일반 부원에게도 공개할지 결정한다.
5. 활동 기록 승인 전 공개 범위와 보완 요청 기한을 결정한다.
6. 공개 푸터에 표시할 공식 동아리명, 대표 문의 수단, 개인정보 담당자와 SNS를 확정한다.
7. 현장 QR 입장 장애 시 수동 확인 기준과 담당 권한을 정한다.
