# 2026-07-25 품질·보안·운영 감사

## 결론

현재 `origin/dev` (`76a7ead`)는 멤버·권한 범위 검증, 로컬 파일 저장소의 경로
차단과 원자 저장, Markdown 정화, 활동 기록 상태 이력 등 핵심 기반이 견고하다.
다만 공유 공지의 예약 상태, 자료실 링크 미리보기, 동시 편집 충돌은 운영 전에
보완해야 한다. 이 문서는 구현 변경이 아니라 수정 우선순위와 수용 기준을 기록한
감사 결과다.

| 등급 | 건수 | 배포 판단 |
| --- | ---: | --- |
| P1 | 4 | 다음 기능 배포 전 수정 권장 |
| P2 | 5 | 운영 초기 전 또는 다음 스프린트에 수정 |
| P3 | 3 | 컨벤션·회귀 방지 항목 |

## 범위와 방법

- 기준 커밋: `origin/dev`의 `76a7ead`
- 범위: Spring Controller·Service·Mapper/XML·Flyway·JSP·공통 JS·보안 설정·테스트·정본 문서
- 정적 검사: MyBatis `${}`/JSP scriptlet/`escapeXml="false"`/인라인 이벤트/
  사용자 데이터 `innerHTML`/`@Data`/`System.out`/Controller→Mapper 의존성 여부
- UI 근거: 현재 JSP·CSS와 이전에 공유된 데스크톱·모바일 캡처를 대조했다.
- 제한: 이 감사 세션에는 브라우저 자동화와 실제 iPhone Safari가 연결되지 않아,
  HTTP·키보드·뷰포트의 실행 검증은 수행하지 않았다. 아래 UI 항목은 실제 기기
  회귀 테스트가 필요하다.

## 우선 수정 항목

### P1-01. 예약 공지의 공유 링크가 예약 시각 이후에도 404가 된다

**근거**

- `InternalNotice.isPubliclyVisible()`은 `SCHEDULED`와 `PUBLISHED`를 공개 가능 상태로
  판단한다.
- `InternalNoticeService.issuePublicShare()`도 이 판단을 사용한다.
- 반면 `InternalNoticeMapper.lookupPublicShare`는 `status_code = 'PUBLISHED'`만 조회한다.

**재현**

1. 미래 시각으로 예약 공지를 만든다.
2. 예약 시각이 지난 뒤 작성자·관리자가 공유 링크를 발급한다.
3. `/share/notices/{token}`은 유효 기간 안인데도 404가 된다.

**영향**: 외부 공유 안내와 실제 로그인 복귀 흐름이 깨진다. 예약 공지의 상태를
배치로 `PUBLISHED`로 바꾸지 않는 현재 구조에서는 지속적인 기능 오류다.

**수정 방향**: 공개 조회도 `SCHEDULED`와 `PUBLISHED`를 허용하되 게시 시작·종료 조건을
동일하게 적용한다. 또는 예약 시각에 상태를 전환하는 신뢰 가능한 작업을 도입한다.
두 방식 중 하나만 정본으로 정하고 Service·Mapper·문서를 일치시킨다.

**수용 기준**: 예약 시작 전에는 404, 시작 후에는 공유 안내 페이지, 종료·보관·삭제·
토큰 철회 후에는 404여야 한다. `SCHEDULED` 공유 토큰을 다루는 Mapper·Service·Controller
테스트를 추가한다.

### P1-02. 자료 링크 카드 수집은 DNS 재바인딩 SSRF를 완전히 막지 못한다

**근거**: `ResourceLinkPreviewFetcher.execute()`는 `validate()`에서 DNS를 조회해
사설 주소를 차단한 뒤 `Jsoup.connect(hostname)`으로 다시 호스트명을 해석해 접속한다.
검증과 실제 연결 사이에 공격자 DNS 응답이 바뀌면 내부 IP로 연결될 수 있다.

**영향**: 로그인 멤버가 자료에 URL을 넣는 것만으로 애플리케이션이 접근 가능한
내부 서비스·메타데이터 엔드포인트에 요청을 보낼 수 있다.

**수정 방향**: 검증한 IP로 실제 연결을 고정하는 HTTP 클라이언트/커스텀 DNS resolver를
사용하거나, 애플리케이션 컨테이너의 egress 방화벽에서 사설·링크 로컬·메타데이터 주소를
차단한다. IPv4·IPv6 예약 대역 검증도 명시적으로 보강한다. 리다이렉트 대상마다 같은
검증을 유지한다.

**수용 기준**: 공인 IP→사설 IP로 바뀌는 DNS 재바인딩, IPv6 loopback/ULA/link-local,
리다이렉트, 사용자 정보 포함 URL, 비 HTML 응답을 모두 차단하는 통합 테스트가 있어야 한다.

### P1-03. 링크 카드 원격 요청이 DB 트랜잭션과 행 잠금을 붙잡는다

**근거**: `ResourceService.create()`·`update()`는 `@Transactional` 안에서
`replacePreviews()`를 호출한다. `update()`는 `FOR UPDATE`로 자료 행을 잠근 뒤 최대 5개
URL과 대표 이미지를 동기적으로 가져온다. 각 요청은 최대 3초이며 이미지도 내려받는다.

**영향**: 느린 외부 사이트 하나가 자료 수정 트랜잭션과 잠금을 수 초~수십 초 유지한다.
동일 자료의 수정·삭제·공유 토큰 변경이 대기하고 DB 커넥션도 오래 점유한다.

**수정 방향**: 자료 본문·첨부 변경만 짧은 트랜잭션으로 확정한 뒤, after-commit 작업 또는
내구성 있는 작업 큐에서 미리보기를 수집한다. 화면에는 “링크 정보를 불러오는 중/실패”를
표현하고, 오래된 미리보기 교체의 원자성 규칙을 정한다.

**수용 기준**: 외부 서버가 timeout이어도 자료 저장은 정해진 짧은 시간 안에 성공하며,
동일 자료의 후속 변경이 불필요하게 lock wait 하지 않는다. timeout·부분 실패·재시도 테스트를 둔다.

### P1-04. 공지·자료·활동 기록·소품의 동시 편집은 마지막 저장이 앞선 변경을 덮어쓴다

**근거**: 주요 수정 Mapper는 `updated_dttm`을 조회하지만 수정 `WHERE` 절에는 기대 버전이
없다. Service의 `FOR UPDATE`는 저장 요청의 순서만 직렬화할 뿐, 오래 열린 편집 화면의
내용을 감지하지 못한다.

**영향**: 운영진 두 명이 같은 공지·자료·활동 기록·소품을 수정하면 뒤늦게 저장한 사람이
앞선 사람의 본문·첨부·상태 정보를 조용히 덮어쓴다. 이력만으로는 즉시 복구가 어렵다.

**수정 방향**: 상세 응답의 `updatedDttm` 또는 별도 `version`을 수정 요청에 포함하고,
`UPDATE ... WHERE updated_dttm = #{expectedUpdatedDttm}`(또는 version 증가)으로 낙관적 잠금을
적용한다. 0건 갱신은 409으로 반환하고 화면은 입력을 유지한 채 새 데이터 확인을 안내한다.

**수용 기준**: 동일 레코드를 두 세션에서 편집할 때 첫 저장만 성공하고 두 번째 저장은 409,
입력 보존, 새로고침/병합 안내가 일관되게 동작해야 한다.

## 운영 초기 보완 항목

### P2-01. 학교 계정 실패 제한은 타깃 계정 잠금 유도 위험이 있다

`school_login_attempt`는 학번 HMAC 단위로 5회 실패 뒤 15분 차단한다. 학교 포털의 실제
잠금을 줄이는 목적에는 맞고, `SELECT FOR UPDATE`로 동시 갱신도 안전하다. 다만 학번 형식이
예측 가능하므로 제3자가 특정 학번에 의도적으로 실패 요청을 보내 정당 사용자의 로그인을
15분 막을 수 있다.

**권장**: 현재 학생번호 단위 제한은 유지하되 IP/세션 단위의 별도 속도 제한, 점진적 지연 또는
CAPTCHA, 차단 건수 모니터링을 더한다. 학교 SSO 호출 전의 차단 원인을 사용자에게 과도한
계정 존재 정보 없이 표시한다.

### P2-02. 일반 첨부와 교체 전 소품 사진의 수명주기가 닫혀 있지 않다

공지·자료의 첨부 관계를 제거하거나 자료를 소프트 삭제하면 `stored_file`과 디스크 객체는
미연결 상태로 남는다. 소품 사진 교체도 새 파일 연결만 갱신하고 이전 사진을 퇴역 manifest에
넣지 않는다. 프로필 사진과 자료 링크 카드 대표 이미지는 재시도 가능한 퇴역 manifest가 있어
대조적으로 관리된다.

**영향**: 저장 공간 증가와 더 이상 사용자 흐름에서 찾을 수 없는 개인정보 파일의 장기 보관.

**권장**: 참조 도메인별 명시적 퇴역 manifest 또는 전역 참조 검사 기반 정리 정책을 만든다.
소프트 삭제된 소품의 현재 사진은 복구 목적상 보존하되, **교체된** 사진만 안전하게 퇴역한다.
보존 기간·재시도·공유 참조 차단 규칙을 문서화한다.

### P2-03. `audit_log`는 중요한 운영 행위를 충분히 포괄하지 않는다

현재 감사 이벤트는 멤버 팀·기수·역할·상태 변경과 소품 삭제·복구에 한정된다. 활동 기록은
별도 검수 이력이 남지만, 공지·자료의 게시/보관/삭제/공유 링크 발급·철회 및 소품 일반 수정은
전역 감사 대상으로 남지 않는다.

**권장**: 도메인 이력과 `audit_log`의 책임을 문서로 구분한 뒤, 외부 노출이나 운영 판단에
영향을 주는 상태 변경을 감사 이벤트에 포함한다. 본문·전화번호·첨부 원문 같은 민감값을
감사 상세에 기록하지 않는 현재 원칙은 유지한다.

### P2-04. 삭제된 공개 도메인의 `permitAll` matcher가 남아 있다

`SecurityConfig`에는 현재 Controller가 없는 `/performances/**`, `/reserve/**`,
`/api/public-notices/**`, `/api/public-performances/**`, `/api/public-policies/**`,
`/api/public-reservations/**` matcher가 남아 있다. 지금은 404이지만 향후 같은 경로를
다시 만들면 의도치 않게 공개될 수 있다.

**권장**: 실제 공개 엔드포인트(`/share/**`, 로그인·정적 자원 등)만 명시적으로 남기고,
폐기 도메인 matcher를 제거한다. 404 회귀 테스트도 함께 둔다.

### P2-05. 대형 화면의 콘텐츠 폭 규칙이 화면마다 일관되지 않다

공통 레이아웃은 `max-w-screen-2xl`이지만 공지·자료 작성은 `max-w-5xl`, 상세는 `max-w-4xl`,
일부 목록·캘린더는 넓은 컨테이너를 사용한다. 공유된 ultrawide 캡처에서는 캘린더·목록이
과도하게 넓거나, 반대로 콘텐츠가 넓은 여백 속에 작게 남는 사례가 있었다.

**권장**: 화면 유형별 최대 폭을 정본화한다.

| 유형 | 권장 폭 |
| --- | --- |
| 읽기·작성 본문 | 64~80rem |
| 일반 목록·카드 | 80~96rem |
| 캘린더·데이터 표 | 96rem~2xl, 최소 읽기 폭 보장 |

1440px와 2560px에서 내용 폭·행 길이·카드 열 수를 시각 회귀 테스트로 고정한다.

## 개선·회귀 방지 항목

### P3-01. 수동 생성자 주입이 프로젝트 표준과 다르다

`FileService`, `InternalNoticeService`, `ResourceService`는 수동 생성자(일부는 생성자에
`@Autowired`)를 쓴다. 필드 주입은 아니므로 동작상 위험은 없지만, 컨벤션 9장의
`private final` + `@RequiredArgsConstructor` 표준에서 벗어나 구현 차이를 늘린다.

### P3-02. 로그인 복귀 검증은 같은 host만 비교한다

`SafeSavedRequestAuthenticationSuccessHandler`는 저장된 요청의 host를 비교한다. SavedRequest가
서버 생성값인 현재 구조에서 즉시 오픈 리다이렉트는 확인되지 않았지만, 프록시·포트·스킴
설정 변화에 대비해 상대 경로만 복귀 대상으로 허용하거나 scheme·host·port를 함께 검증하는
편이 안전하다.

### P3-03. 링크 미리보기 시간은 주입 가능한 Clock을 사용하지 않는다

`ResourceLinkPreviewFetcher`가 `LocalDateTime.now()`를 직접 호출한다. 기능 오류는 아니나,
시간 경계 테스트와 재현성을 위해 프로젝트의 `Clock` 빈을 사용하는 편이 일관된다.

| 공유 링크로 내부 데이터 노출 | 익명 공유 페이지는 제목과 안내만 제공하고 로그인 후 원래 인가를 통과 | 양호 |

## 확인한 긍정 요소

- 파일 바이너리를 DB가 아닌 로컬 영구 저장소에 두고, DB에는 키·해시·상태만 보관한다.
- `LocalFileObjectStorage`는 경로 이탈을 막고 임시 파일 후 원자 이동을 사용한다.
- Markdown은 서버에서 정화한 결과만 렌더링하며 원시 HTML·`javascript:` URL을 막는다.
- 권한은 `SecurityConfig`의 1차 경계와 Service의 팀·대상 재검증으로 이중 확인한다.
- 멤버 팀·기수·역할·상태 이력, 활동 검수 이력, 소프트 삭제 조회 조건이 명확하다.
- 정적 검사에서 MyBatis `${}`, JSP scriptlet, `escapeXml="false"`, `@Data`,
  `System.out`, `printStackTrace`, Controller→Mapper 의존성을 발견하지 못했다.
- 정적 온보딩 안내 화면은 `feature-spec`의 “동적 온보딩은 후속 범위, 정적 안내 제공” 정책과
  일치한다.
