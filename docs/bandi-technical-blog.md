# 기능을 만드는 것보다 운영 가능한 경계를 만드는 일

## bandi를 설계하고 구현하며 배운 것들

bandi는 연극 동아리 구성원이 학교 계정으로 로그인해 일정, 공지, 자료, 활동 기록,
소품·장비와 멤버 정보를 함께 관리하는 내부 운영 서비스다.

처음에는 “동아리 관리 사이트를 만들자”는 말에서 시작했다. 그러나 실제 구현은 화면을
만드는 일만으로 끝나지 않았다. 학교 SSO가 어떤 방식으로 동작하는지 확인해야 했고, 파일을
어디에 저장할지 결정해야 했고, 팀장과 관리자의 권한 경계를 매 요청마다 어떻게 지킬지
정해야 했다. 공지와 자료실은 단순한 게시판이 아니라 카카오톡·Discord 같은 외부 플랫폼에
공유될 수 있는 콘텐츠가 되었고, 활동 기록은 웹 입력값을 한글에서 열리는 HWPX 문서로
변환해야 했다.

이 글은 현재 `dev` 기준의 구현과 문서를 바탕으로, 그 과정에서 했던 기술적 선택과 실제로
발생한 문제, 그리고 아직 남은 개선 과제를 정리한 개발 회고다.

---

## 1. 처음부터 지켜야 했던 제약

bandi의 기술 선택은 유행보다 운영 조건에서 출발했다.

- 학교 SSO를 사용하므로 자체 비밀번호 계정을 만들지 않는다.
- 로그인은 JWT가 아닌 세션 기반으로 유지한다.
- JSP가 실행형 JAR에서 지원되지 않으므로 WAR로 패키징한다.
- 멤버 수가 동아리 규모인 만큼 SPA를 새로 도입하지 않고 Spring MVC + JSP/JSTL을 유지한다.
- DB는 MySQL, SQL 접근은 MyBatis XML, 스키마 변경은 Flyway로 관리한다.
- 파일 바이너리는 DB BLOB으로 저장하지 않고 서버의 영구 디스크에 둔다.
- 기능 간 참조는 Controller나 Mapper가 서로 침범하지 않고 Service를 통해서만 연결한다.

최종 구조는 다음과 같다.

```text
Browser
  ├─ JSP SSR Controller
  └─ REST /api Controller
          │
          ▼
       Service  ───── 다른 feature의 Service
          │
          ▼
       MyBatis Mapper
          │
          ▼
       MySQL + Flyway

       FileService ── Local persistent volume
       Spring Security ── JDBC session + CSRF
```

이 구조는 화려하지 않지만, 누가 데이터를 읽고 바꾸는지와 트랜잭션 경계가 비교적 명확하다.
특히 서버 렌더링과 작은 Vanilla JavaScript를 선택한 것은 프론트 기술을 몰라서가 아니라,
현재 서비스에서 필요한 상태 관리 범위와 배포 복잡도를 줄이기 위한 선택이었다.

### WAR와 JSP를 고른 이유

JSP는 최근 프론트엔드 생태계의 중심은 아니지만, 이 프로젝트에는 몇 가지 장점이 있었다.
첫 화면과 역할별 메뉴를 서버에서 바로 구성할 수 있고, 인증되지 않은 사용자가 보호된
데이터를 잠깐이라도 받은 뒤 브라우저에서 숨기는 구조를 피할 수 있다. 반대로 페이지 내부의
검색·필터·미리보기·파일 업로드 같은 상호작용만 API와 JavaScript로 보완했다.

대신 JSP를 선택한 대가는 명확했다. 사용자 데이터 출력에는 `c:out`을 써야 하고, 인라인
이벤트와 사용자 데이터 `innerHTML`을 피해야 하며, SSR shell과 API 상태를 함께 설계해야
했다. “서버 렌더링이니까 프론트 고민이 적다”는 생각은 틀렸다. 반응형·포커스·빈 상태·오류
상태는 SSR이어도 모두 직접 설계해야 했다.

## 2. SSO: 처음에 실패한 구현이 가장 좋은 명세가 되었다

가장 먼저 어려웠던 부분은 학교 통합인증이었다. 초기 Java 구현은 로그인 페이지를 먼저
열지 않고 곧바로 POST했고, 아이디와 비밀번호를 평문으로 전송했으며, 세션마다 바뀌는
암호화 키도 알지 못했다. 성공 여부도 응답 본문이 아니라 `KSESSIONID` 쿠키 존재 여부로
판단했다.

결과는 당연히 실패였다. 서버는 “세션이 만료되었습니다” 또는 “알 수 없는 오류”를
반환했고, 쿠키는 실패한 로그인에도 발급되기 때문에 성공 판정도 잘못됐다.

### 브라우저 흐름을 그대로 관찰한 PoC

문제를 추측하지 않고 브라우저 요청을 분해했다. Python PoC로 다음 흐름을 재현했다.

```text
1. GET /sso/login_stand.jsp
   └─ KSESSIONID 발급, HTML에 세션별 keyHex 포함

2. 아이디·비밀번호에 현재 시각을 붙임
   plaintext = text + "|" + timestamp_ms

3. AES-128-CBC + PKCS7로 암호화
   key = 방금 GET한 페이지의 동적 keyHex
   iv  = 요청마다 새로 만든 16바이트

4. iv + ciphertext를 Base64 URL-safe 형식으로 인코딩

5. 같은 세션 쿠키로 로그인 POST
6. 응답 본문의 alert/redirect를 기준으로 인증 결과 판정
```

이 실험으로 중요한 사실을 알게 됐다. SSO 연동은 “아이디와 비밀번호를 HTTP로 보내는
기능”이 아니라, 학교 페이지가 요구하는 세션·암호화·응답 판정 프로토콜을 구현하는
어댑터였다.

이후 학교 인증 자체는 `member` 도메인의 `SchoolAuthenticationService`가 담당하고,
`global.security`는 Spring Security와 학교 인증 어댑터를 연결하는 역할로 정리했다. SSO
구현 전체를 global로 옮기면 global이 member 모델과 예외를 알아야 하므로 오히려 패키지
경계가 무너진다는 판단이었다.

### Cloudflare Tunnel에서만 실패했던 이유

로컬에서는 로그인이 되는데 Cloudflare Tunnel을 통해 접근하면 이름 불일치로
`REVIEW_REQUIRED`가 되는 문제가 있었다. 처음에는 HTTPS 리다이렉트나 SSO 파서가
프록시 환경에서 다르게 동작하는 것으로 의심했다.

실제 원인은 DB에 저장된 한글 이름의 이중 인코딩이었다.

```text
정상: 김현민
오류: ê¹€í˜„ë¯¼
```

학번은 같은 멤버를 찾았지만 이름 비교에서 실패했고, 그 결과 SSO 연결이 보류 상태가
됐다. HTTPS가 원인이 아니었다. 이 사건은 외부 연동 장애를 볼 때 애플리케이션 로그만
보지 말고, DB에 실제로 저장된 문자 인코딩과 데이터 길이도 확인해야 한다는 교훈을 줬다.

### SSO 정보의 정본과 갱신

로그인 성공 시 학번을 기준으로 멤버 행을 잠그고 학교에서 받은 학과, 학적, 휴대폰 번호,
마지막 로그인 시각을 갱신한다. 휴대폰 번호는 SSO에서 유효한 숫자 형식이 온 경우에만
교체하고, 응답에 번호가 없거나 이상하면 기존 번호를 지우지 않는다.

학교 비밀번호는 저장하지 않는다. 또한 학교 포털을 계속 틀려 계정이 잠기는 문제를 막기
위해 학번 원문 대신 HMAC 해시를 `school_login_attempt`에 저장하고, 최근 15분 동안 5회
실패하면 15분 동안 SSO 요청 자체를 중지한다. 서버 장애나 멤버 연결 실패를 학교 비밀번호
오류와 동일하게 세지 않는 것도 중요했다.

## 3. 왜 Spring Security를 선택했는가

“필터나 인터셉터로 직접 검사하면 되지 않나?”라는 질문은 구현 과정에서 여러 번 나왔다.
결론부터 말하면 bandi에서는 Spring Security가 더 넓은 인증·보안 수명주기를 맡고, Service가
업무 권한을 최종 검사하는 구조가 적합했다.

### 역할 분담

```text
Spring Security Filter Chain
  ├─ form login
  ├─ JDBC session
  ├─ CSRF
  ├─ URL/역할 1차 경계
  ├─ logout
  └─ Saved Request 기반 로그인 복귀

Service
  ├─ 활성 멤버 여부
  ├─ 자기 팀인지
  ├─ 공지 대상 범위인지
  ├─ 작성자 본인인지
  ├─ 상태 전이가 가능한지
  └─ 데이터 변경과 이력 기록
```

예를 들어 `/team-members`는 LEADER만 접근할 수 있도록 SecurityConfig에서 1차 제한한다.
하지만 팀장이라고 해서 모든 팀 멤버를 바꿀 수 있는 것은 아니다. Service가 현재 팀장인지,
대상 멤버가 같은 팀인지, 대상 팀이 활성인지, 변경 사유가 있는지를 다시 확인한다.

Controller에서 `if (role == ...)`를 반복하지 않는 이유도 여기에 있다. Controller는 HTTP
입력과 응답에 집중하고, 업무 규칙은 Service와 model이 소유해야 한다. 인터셉터는 MVC 요청
전처리에는 유용하지만 CSRF, 세션, 로그인 성공 후 복귀, 인증 객체, 예외 처리까지 일관되게
맡기기에는 직접 구현할 영역이 너무 커진다.

다만 이 구조가 권한 문제를 자동으로 모두 해결해 주는 것은 아니다. 현재 후속 검토에서
활성 정지·탈퇴 멤버의 기존 세션을 얼마나 즉시 무효화할지, 매 요청마다 역할을 갱신하면서
DB를 조회하는 비용을 어떻게 줄일지라는 과제가 발견됐다. URL 경계와 Service 검사는 지키되,
세션 상태의 생명주기는 더 정교하게 다듬을 필요가 있다.

## 4. 데이터 모델: 상태값보다 상태 전이가 더 어렵다

멤버·팀·기수는 단순한 마스터 데이터처럼 보이지만 실제 운영에서는 이력과 복구가 필요했다.

- 팀 변경: `member_team_history`
- 역할 변경: `member_role_history`
- 상태 변경: `member_status_history`
- 기수 변경: `member_cohort_history`
- 감사 정보: `audit_log`
- 권한과 독립적인 회장 직책: `club_officer`

기수는 `1-1`, `1-2` 같은 이름을 가지므로 연도와 학기를 쪼갠 컬럼 대신 문자열 기준정보로
단순화했다. 삭제 대신 신규 추가만 허용해 기존 이력의 의미를 보존했다.

탈퇴는 별도 테이블로 이동하지 않는다.

```text
member.member_status_code = WITHDRAWN
member_status_history에 변경 전/후·사유·처리자·시각 저장
```

이렇게 해야 과거 활동 기록, 파일, 감사 로그의 외래키가 깨지지 않는다. 이후 운영진이
사유를 남겨 `WITHDRAWN → ACTIVE`로 복구할 수 있게 했고, 등록 취소처럼 복구하지 않는
종단 상태와 구분했다.

### Flyway를 고친 파일이 아니라 새 파일로만 쓴 이유

개발 중 이미 적용된 SQL 파일을 수정하면 사람마다 다른 DB가 생기고, 운영·테스트 환경의
스키마 이력을 신뢰할 수 없게 된다. 그래서 기존 Flyway 파일은 그대로 두고, 삭제·컬럼 변경·
제약 변경은 새 버전 파일로 쌓았다.

이 원칙은 한동안 불편했다. “오타 하나만 고치면 되는데 왜 새 migration인가?”라는 상황이
자주 생겼기 때문이다. 하지만 스키마는 소스 코드와 달리 이미 실행된 과거를 다시 쓰면 안
된다. 특히 공연·예약·회비 등 폐기한 서비스의 테이블이 Flyway 이력에 남아 있는 것과
현재 코드에서 더 이상 사용하지 않는 것은 서로 다른 문제다. 과거 이력을 지우기보다 새
정리 migration과 현재 feature 범위를 분리하는 편이 안전하다.

## 5. 파일 저장소: MinIO를 버리고 로컬 디스크를 택한 이유

초기에는 MinIO를 고려했다. 그러나 현재 테스트 서버와 동아리 운영 규모에서 별도 객체
스토리지, 버킷, presigned URL, 권한 정책을 추가로 운영하는 비용이 컸다. 팀 공유 서버에
이미 영구 디스크와 중앙 Cloudflare Tunnel이 있고, 파일을 내부 서비스에서만 권한 확인 후
제공하면 충분했다.

그래서 최종 구조는 다음과 같다.

```text
FILE_STORAGE_ROOT=/data/bandi
  ├─ private/
  └─ public/

stored_file
  ├─ original_name
  ├─ storage_scope_code
  ├─ storage_key
  ├─ content_type
  ├─ size_bytes
  ├─ sha256_hash
  ├─ upload_status_code
  └─ uploaded_by_member_id
```

DB에는 파일 바이너리가 들어가지 않는다. `storage_key`는 애플리케이션이 만든 상대 경로이고,
실제 파일은 `/data/bandi` 아래에 저장된다. 다운로드는 presigned URL이 아니라 Spring Boot가
feature 권한을 확인한 뒤 직접 스트리밍한다.

### DB와 파일 시스템은 하나의 트랜잭션이 아니다

파일 저장에서 가장 중요한 상태는 `PENDING → READY/FAILED`다.

1. 파일 내용·실제 MIME·크기·해시를 검사한다.
2. DB에 `PENDING` 메타데이터를 만든다.
3. 임시 파일에 스트리밍하고 원자적으로 이동한다.
4. 저장 검증값을 기록하고 `READY`로 바꾼다.
5. 실패하면 객체 삭제를 보상 시도하고 `FAILED`를 남긴다.

DB 트랜잭션이 성공했다고 파일 시스템 저장까지 성공한 것은 아니다. 반대로 파일이 저장된
뒤 DB 트랜잭션이 롤백될 수도 있다. 프로필 사진 교체, 링크 카드 대표 이미지, 공지 첨부
정리에는 retirement manifest를 두어 파일 삭제 실패를 재시도할 수 있게 했다.

여기서 얻은 교훈은 “로컬 디스크는 간단하다”와 “파일 일관성은 간단하다”가 같은 말이
아니라는 것이다. 단일 서버에서 운영하기에는 로컬 디스크가 단순하지만, 백업·복구·고아
파일 정리·디스크 용량 모니터링은 반드시 운영 절차로 남겨야 한다.

## 6. 공지와 자료실: Markdown을 허용하되 HTML은 믿지 않는다

공지와 자료실은 처음에 짧은 입력 모달에 가까웠지만, 실제 사용 목적은 동아리 내부 자료를
기록하고 카카오톡·Discord 등에 공유하는 것이었다. 그래서 목록·상세·작성·수정 페이지를
분리하고, 제목과 작성자·수정 시각·첨부를 명확히 보여 주도록 바꿨다.

### Markdown 신뢰 경계

DB에는 Markdown 원문만 저장한다. 렌더링된 HTML을 저장하지 않고, 서버가 매번 안전한 HTML을
생성한다.

허용 범위는 제목, 서식, 목록, 인용, 코드 블록, 표, 링크 등 GFM의 실용적인 일부다. 다음은
차단한다.

- 원시 HTML
- `javascript:`와 `data:` URL
- 이벤트 속성
- 외부 iframe
- 검증되지 않은 이미지

공지 본문 이미지는 `attachment://{storedFileId}` 내부 참조를 통해 첨부 파일과 연결한다.
자료실의 단독 HTTPS URL은 서버가 Open Graph 메타데이터를 수집해 링크 카드 스냅샷으로 저장한다.
열람자의 브라우저가 외부 사이트나 대표 이미지를 직접 요청하지 않도록 한 것이 개인정보와
안정성 측면에서 중요했다.

### URL 미리보기의 숨은 위험

URL 카드 하나를 만드는 일은 단순히 `GET` 한 번 하는 일이 아니다. 사용자가 입력한 URL을
서버가 요청하므로 SSRF가 될 수 있다.

- localhost와 사설 IP 차단
- DNS 해석 후 예약·사설 주소 검증
- 리다이렉트마다 대상 재검증
- HTTPS와 HTML 응답만 허용
- 응답 크기·리다이렉트 횟수 제한
- 인증 헤더·쿠키 전송 금지
- 대표 이미지 저장 시에도 동일한 검증 적용

현재 설계에 이 방어선은 반영되어 있지만, 후속 품질 검토에서 DNS rebinding, 원격 fetch를
DB 트랜잭션 안에서 수행하는 문제, 링크 카드 이미지 퇴역을 더 엄격하게 다뤄야 한다는 과제가
남았다. 외부 네트워크 요청은 트랜잭션과 분리하고, 제한 시간과 실패 정책을 별도 경계로
두는 것이 다음 단계다.

### 공유 링크의 타협

게시글을 외부 플랫폼에서 미리 보여 주려면 비로그인 URL이 필요하지만, 본문과 첨부까지
공개하고 싶지는 않았다. 그래서 공유 토큰은 제목과 “로그인 후 내용을 확인할 수 있어요”라는
안내만 제공한다.

```text
/share/notices/{256-bit random token}
/share/resources/{256-bit random token}

비로그인: 제목 + 로그인 안내 + noindex/no-store
로그인 후: 원래 상세 URL로 이동, 기존 권한 재검사
```

토큰은 추측 불가능한 Base64URL 256비트 난수이며 DB에는 토큰만 nullable unique로 저장한다.
공유를 중단하면 NULL로 바꾸어 기존 링크를 즉시 무효화한다. 단, 외부 플랫폼이 이미 저장한
미리보기 캐시는 애플리케이션에서 즉시 지울 수 없다는 점도 사용자에게 알려야 했다.

## 7. HWPX: 웹 폼과 문서 포맷 사이의 경계를 다루다

활동 내역서 기능은 일반 게시글과 달랐다. 사용자가 웹에서 대표자, 장소, 활동 일시, 사진,
내용, 참여자를 입력하면 기존 동아리 양식과 같은 `.hwpx`를 만들어야 했다.

HWPX는 단순한 텍스트 파일이 아니라 ZIP 안에 OWPML XML, manifest, 이미지와 미리보기 정보가
들어 있는 문서 포맷이다. PDF나 DOCX로 우회하지 않고, 제공된 양식을 기준으로 별도 개인정보
제거 템플릿을 만들었다.

```text
템플릿 복사
  → 지정된 XML 표·셀·문단 탐색
  → [TITLE], [P01_NAME] 같은 표식 검증
  → 사용자 텍스트를 XML text node로 삽입
  → 사진 EXIF 방향 적용·메타데이터 제거
  → 이미지 참조·manifest·CRC 검증
  → HWPX 응답 또는 활동 기록 파일로 저장
```

전체 XML 문자열을 무차별 치환하지 않고 namespace-aware DOM으로 지정된 셀만 찾아 바꾼
이유는, 같은 문구가 안내 문구나 다른 셀에 우연히 존재할 수 있기 때문이다. 사용자 텍스트는
XML 노드로 넣어 `<`, `>`, `&`, 한글과 줄바꿈이 문서를 깨뜨리지 않도록 했다.

참여자는 양식의 표시 한계 때문에 최대 14명으로 제한했고, 총계는 입력받지 않고 행 수로
계산했다. 회장 이름은 `ADMIN` 같은 권한과 별개의 `club_officer` 직책에서 현재 활성
회장을 조회한다. 배포 없이 DB의 직책만 바꾸면 다음 문서에 반영된다.

### 실제로 발견한 사진 방향 버그

웹 브라우저에서는 사진이 정상으로 보였지만 한글에서 열면 사진이 거꾸로 나오는 문제가
있었다. 원본 이미지의 EXIF Orientation과 픽셀 방향을 다르게 처리했기 때문이다. 브라우저는
EXIF를 해석해 보여 줄 수 있지만, 문서에 삽입한 이미지의 픽셀은 이미 회전이 반영돼 있어야
한다.

따라서 서버에서 EXIF 방향을 적용한 새 이미지로 정규화한 뒤 메타데이터를 제거하고, 4:3
영역에 비율을 유지한 contain 방식으로 삽입했다. 이 문제는 “웹에서 잘 보인다”가 “다운로드한
문서에서도 잘 보인다”를 보장하지 않는다는 좋은 사례였다.

### 활동 기록과 HWPX를 하나의 검수 흐름으로 통합

처음에는 “활동 기록”과 “활동 내역서 만들기”가 서로 다른 기능처럼 보였다. 실제로는 같은
활동을 기록하고 검수하는 과정의 두 입력 형식이었다. 최종 모델은 다음 상태를 정본으로
사용한다.

```text
DRAFT
  → SUBMITTED
  → TEAM_APPROVED
  → APPROVED
  → ARCHIVED

TEAM_APPROVED 또는 SUBMITTED
  → REVISION_REQUESTED
  → SUBMITTED
```

간단 활동 기록은 사진 없이 제출할 수 있지만, HWPX 형식은 증빙 사진과 생성 문서가 모두
있어야 제출할 수 있다. 팀장은 자기 팀의 제출물을 1차 검수하고, 관리자는 최종 승인한다.
관리자는 긴급 최종 승인 사유를 남길 수 있고, 본인이 작성한 기록도 관리자 최종 검수 범위에
포함한다. 반대로 작성자가 팀장이라는 이유만으로 자기 기록을 팀장 검수하는 것은 허용하지
않는다.

초기에 상태가 맞지 않는데 “검수 요청”을 누르면 `InvalidActivityRecordStateException`이
발생했다. 로그상 파일과 revision은 정상인데 상태 전이가 불가능했던 것이다. 이 사건은
오류를 단순히 버튼 숨김으로 해결하지 말고, model의 전이 규칙·Service의 권한·화면의 현재
상태 표시를 함께 맞춰야 한다는 것을 보여 줬다.

## 8. 캘린더와 소품·장비: 현장 사용성을 기준으로 다시 만든 화면

### 직접 만든 캘린더의 한계

초기 캘린더는 직접 만든 월간 격자였다. 일정이 많지 않을 때는 작동했지만, 월·주·목록
전환, 긴 일정, 키보드 접근, 모바일 재배치, 날짜 선택을 직접 관리하기 시작하면 화면 코드가
빠르게 복잡해졌다.

그래서 FullCalendar 7.0.1을 월·주·목록 표시 엔진으로 사용하고, 날짜·시간 입력은 Vanilla
Calendar Pro 3.1.0과 네이티브 `datetime-local` fallback으로 통일했다. 모바일이나 JavaScript
초기화 실패 상황에서도 입력을 완전히 막지 않는 것이 핵심이었다.

종일 일정은 사용자에게 마지막 날을 포함해서 보여 주지만 서버에는 다음 날 00:00의 배타적
종료값으로 저장한다. 기간 조회는 다음 반개구간 조건을 쓴다.

```sql
start_dttm < :range_end
AND end_dttm > :range_start
```

이렇게 해야 경계에서 끝난 일정이 다음 기간에 중복으로 나타나지 않는다. 다만 드래그로
즉시 일정을 바꾸거나 낙관적 잠금을 적용하는 기능은 의도적으로 넣지 않았고, 일정 편집 충돌은
후속 과제로 남겼다.

### 소품·장비는 “조회”보다 “현장 촬영”이 중요했다

소품 화면은 데스크톱 표를 모바일에서 축소하는 방식으로는 부족했다. 현장에서는 휴대폰으로
사진을 찍고 품목을 찾고 상태를 확인한다. 그래서 목록은 데스크톱 썸네일 행, 모바일 카드로
분리하고 등록·수정은 전용 페이지로 구성했다.

모바일 파일 input에는 `accept="image/*"`, `capture="environment"` 힌트를 주되, 기기와
브라우저가 앨범 선택을 막지 않도록 했다. 사진을 선택하면 Object URL로 즉시 미리보고,
교체·이탈 시 URL을 해제한다. 사진 삭제는 별도 기능으로 만들지 않고 교체만 지원하며,
품목 삭제는 ADMIN의 소프트 삭제·복구로 제한했다.

## 9. UI/UX에서 가장 많이 배운 것

초기 화면은 목업을 충실히 옮겼지만 실제 업무 화면으로는 불편한 부분이 많았다. 모든 것을
카드로 감싸고, 설정을 본문 아래에 둔 뒤, 모바일에서는 데스크톱 배치를 그대로 줄이는
식이었다.

반복해서 적용한 원칙은 다음과 같다.

1. 한 화면은 하나의 핵심 행동을 돕는다.
2. 상태값보다 사용자가 지금 해야 할 행동을 먼저 보여 준다.
3. 본문은 흰색 읽기 표면으로 분리한다.
4. 위험 작업은 결과와 복구 방법을 함께 설명한다.
5. 모바일에서는 44px 터치 영역, 키보드와 포커스, 고정 버튼 겹침을 먼저 확인한다.
6. 와이드 모니터에서는 콘텐츠가 화면 전체로 늘어나지 않도록 읽기 폭을 제한한다.
7. 브라우저 native select는 OS별 모양이 다르므로, 모바일에서 가려지는 레이어와 포커스
   상태를 따로 검증한다.

공지 작성 화면에서 중요 공지와 예약 게시를 어디에 배치할지 여러 번 바꾼 것도 같은 이유다.
“구현 규칙에 맞다”와 “사용자가 자연스럽게 이해한다”는 별개의 기준이었다. 자료실도 공지와
동일한 Markdown 편집·미리보기 패턴을 공유하고, 활동 기록은 HWPX 생성과 일반 활동 기록을
하나의 시작 버튼에서 선택하도록 정리했다.

권한에 따른 메뉴도 중요한 UX였다. 일반 멤버에게 승인 기록, 활동 검수, 팀 멤버 관리,
멤버 권한 메뉴가 보이면 실제 접근 권한이 없더라도 사용자는 오류라고 생각한다. 권한은
보안의 문제이면서 동시에 내비게이션 정보 구조의 문제였다.

## 10. PWA와 로그인 화면: 설치성은 주되 오프라인 데이터는 캐시하지 않기

PWA는 오프라인 업무 앱으로 만들지 않았다. 내부 공지, 멤버 정보, 활동 기록은 오래된 데이터가
노출되면 안 되고, 세션 기반 서비스는 네트워크 없이 정상 동작한다고 약속하기 어렵다.

그래서 manifest, 아이콘, 최소 service worker만 제공하고, GET 요청을 캐시하지 않는 정책을
택했다. PWA 설치 경험은 제공하지만 오프라인 데이터 저장·동기화 큐는 제공하지 않는다.

로그인 화면에는 동아리 사진 슬라이더와 브랜드 로고를 넣었고, 웹사이트 favicon과 PWA 아이콘의
용도를 구분했다. 여기서도 “같은 로고를 썼는가”보다 “브라우저 탭, 설치 아이콘, 좁은 화면에서
식별 가능한가”를 기준으로 봤다.

## 11. CI/CD: 처음 실패한 배포가 운영 경계를 알려 줬다

테스트 서버에는 이미 MySQL과 중앙 Cloudflare Tunnel이 실행되고 있었다. Bandi는 테스트
서버에서 Docker Compose로 앱만 재배포해야 했다.

초기 GitHub Actions 실행은 hosted runner에서 `docker compose`를 실행하려고 했고, 다음과
같이 실패했다.

```text
docker: command not found
```

또한 Bandi Compose가 중앙에서 별도로 운영하는 Cloudflare Tunnel 토큰까지 요구하고 있었다.
이것은 배포 대상의 경계를 잘못 잡은 설계였다.

최종 방향은 다음과 같다.

```text
Pull Request
  → GitHub hosted runner에서 build/test

dev push
  → Ubuntu x64 self-hosted runner
  → docker compose --env-file /etc/bandi/.env.test
  → app만 --no-deps --build 재생성
  → 기존 MySQL 컨테이너·볼륨 유지

Cloudflare Tunnel
  → 중앙 인프라에서 별도 운영
```

테스트 서버 환경 파일은 `/etc/bandi/.env.test`에 두고, 파일 저장 경로는 `/data/bandi`로
고정했다. 배포 과정에서 `docker compose down -v`를 사용하지 않는 것이 핵심이다. DB 마이그레이션은
앱 기동 시 Flyway가 수행하지만, 마이그레이션은 스키마를 변경하는 작업이지 기존 데이터를
임의로 지우는 배포 작업이 아니다. 파기 migration이 필요한 경우에는 별도 승인과 백업·복구
절차가 먼저다.

Self-hosted runner는 Docker socket에 접근할 수 있는 만큼 신뢰 경계를 명확히 해야 한다.
아무 브랜치나 배포하지 않고 dev의 검증된 워크플로우만 배포 대상에 두며, 환경 파일은 runner에
읽기 전용으로 제공한다. CI/CD는 “자동으로 잘 배포된다”보다 “무엇을 절대 건드리지 않는가”가
더 중요했다.

## 12. 테스트와 검수: 빌드 성공만으로는 부족했다

모델과 Service는 TDD를 원칙으로 삼았다.

```text
테스트 목록 작성
  → Red: 실패를 확인
  → Green: 최소 구현
  → Refactor: 테스트를 유지한 채 정리
```

실제 테스트가 잡아낸 문제도 있었다.

- 팀 seed 데이터에서 누락된 팀을 발견했다.
- MyBatis의 숫자 별칭이 `Integer`로 해석되는 문제를 찾았다.
- Clock 빈이 없어 Spring 컨텍스트가 뜨지 않는 문제를 찾았다.
- HWPX 이미지 EXIF 방향 오류를 발견했다.
- 상태 전이가 허용되지 않는 활동 기록에 검수 요청을 보내는 문제를 드러냈다.

화면은 `./gradlew build`만으로 검증되지 않는다. 320×800, 375×812, 768×1024,
1440×900에서 직접 확인하고, 긴 제목·긴 학과명·긴 파일명·빈 목록·API 오류·모바일 키보드·
Escape·Tab 포커스를 봐야 했다. 와이드 모니터에서 모든 화면이 지나치게 늘어나거나, 모바일
native select가 콘텐츠를 가리는 문제는 정적 테스트보다 캡처 검수에서 더 빨리 드러났다.

품질 검토에서 추가로 확인한 후속 위험은 다음과 같다.

- 링크 카드 수집의 DNS rebinding과 트랜잭션 내 원격 요청
- 동시 편집 시 마지막 저장이 이전 변경을 덮는 문제
- 정지·탈퇴 멤버의 기존 세션 즉시 무효화
- 실패한 첨부·교체 파일의 고아 정리
- 모든 운영 변경이 audit log에 빠짐없이 남는지 여부
- 요청마다 역할을 갱신할 때 발생하는 DB 조회 비용

이 목록은 “현재 기능이 작동한다”와 “운영 환경에서 오래 안전하게 작동한다” 사이의 차이를
보여 준다.

## 13. 기술 선택을 질문받았을 때의 짧은 답

### 왜 Spring Security인가?

인증·세션·CSRF·로그아웃·Saved Request·URL 역할 경계를 검증된 필터 체인으로 관리하고,
서비스 도메인 권한은 Service에서 별도로 검사하기 위해서다. 인터셉터 하나로 이 전체 수명
주기를 대체하지 않았다.

### 왜 MyBatis인가?

목록·권한·소프트 삭제·count 쿼리·기간 겹침 조건처럼 SQL이 업무 의미를 직접 드러내야 하는
부분이 많았다. XML SQL을 정본으로 두되 `${}`를 금지하고, 동적 정렬은 whitelist로 제한했다.

### 왜 파일을 DB BLOB으로 저장하지 않았나?

사진과 HWPX를 DB에 넣으면 DB 백업·복구·버퍼·쿼리 비용이 커진다. 파일은 디스크, DB는
메타데이터와 권한 연결을 담당하게 분리했다. 대신 파일 시스템 실패를 `PENDING/READY/FAILED`
와 retirement manifest로 다뤘다.

### 왜 MinIO를 사용하지 않았나?

현재 단일 테스트 서버 운영 범위에서 별도 객체 저장소의 운영 복잡도가 이득보다 컸다.
대신 `/data/bandi` 영구 볼륨, 백업 절차, 디스크 모니터링을 운영 책임으로 명시했다. 향후
다중 서버·고가용성·대규모 파일이 필요해지면 object storage 전환을 다시 검토할 수 있다.

### 왜 TypeScript를 쓰지 않았나?

현재 프론트는 JSP와 Vanilla JavaScript를 유지하는 프로젝트 제약이 있고, 새 npm 빌드 체인을
추가하지 않았다. 따라서 JS 금지 규칙, 공통 API wrapper, `data-action`, DOM text node 사용,
문법 검사로 안정성을 확보했다. 화면 복잡도가 커지면 TypeScript 전환은 별도 프로젝트로
판단해야 한다.

### 왜 조회수를 넣지 않았나?

공지의 운영 목적은 누가 확인했는지이지 단순한 페이지 조회량이 아니었다. 멤버별 읽음 상태를
저장하면 운영진이 실제 확인 여부를 볼 수 있고, 조회수에 필요한 동시성 증가도 피할 수 있다.

### 왜 PWA 오프라인 캐시를 하지 않았나?

설치성은 필요하지만 공지·멤버·활동 기록의 오래된 데이터가 오프라인에 남는 것은 원하지
않았다. 현재 PWA는 installability와 반응형 shell만 제공하고, 업무 데이터는 항상 인증된
서버 응답을 사용한다.

## 14. 아직 남은 다음 단계

현재 dev는 핵심 기능을 연결한 상태지만, 다음 작업을 하면 “동작하는 시스템”에서 “운영에
강한 시스템”으로 한 단계 올라간다.

1. **세션 무효화 정책**
   - 멤버가 정지·탈퇴되면 기존 JDBC 세션을 즉시 끊을지 정책을 확정한다.
   - 매 요청 DB 조회와 세션 캐시의 균형을 잡는다.

2. **동시 편집 보호**
   - 공지, 자료, 활동 기록, 일정에 버전 또는 `updated_dttm` 기반 조건부 저장을 적용한다.
   - 충돌 시 입력을 보존한 채 다시 불러올 수 있게 한다.

3. **링크 카드 수집 격리**
   - 원격 메타데이터 수집을 사용자 저장 트랜잭션과 분리한다.
   - DNS·리다이렉트 검증과 시간·크기 제한을 독립 모듈로 테스트한다.

4. **파일 수명주기 운영**
   - PENDING/FAILED/고아 첨부/retirement manifest를 정기적으로 점검한다.
   - `/data/bandi` 백업·복구와 용량 경보를 운영 문서에서 실제 절차로 검증한다.

5. **감사 로그 완결성**
   - 상태 변경, 권한 변경, 파일 파기, 공유 중단 등 운영상 중요한 행동이 모두 동일한
     기준으로 남는지 점검한다.

6. **화면 회귀 자동화**
   - 주요 역할과 뷰포트의 캡처를 자동화하고, 320px·와이드 모니터·Safari에서 레이아웃
     회귀를 반복 검증한다.

## 마무리

bandi를 만들며 가장 크게 바뀐 관점은 “기능을 추가하면 완성된다”는 생각이었다. 실제로는
기능을 추가할수록 경계가 더 중요해졌다.

- SSO와 멤버 데이터의 정본은 어디인가?
- URL 역할 검사와 실제 팀 범위 검사는 어디서 나뉘는가?
- DB 트랜잭션과 파일 시스템 실패를 어떻게 연결하는가?
- Markdown을 편하게 허용하면서 HTML과 외부 네트워크를 어떻게 통제하는가?
- 웹에서 보이는 사진과 다운로드 문서에서 보이는 사진이 같은가?
- 배포가 새 앱을 띄우면서 기존 MySQL과 영구 파일을 건드리지 않는가?
- 권한이 없는 메뉴를 아예 보여 주지 않는가?

이 질문에 답하는 과정에서 bandi의 구조가 만들어졌다. 완벽한 구조라기보다, 현재 규모와
운영 조건에서 선택한 이유를 설명할 수 있고, 나중에 바꿔야 할 지점도 알고 있는 구조에
가깝다.

기술의 성숙도는 사용한 라이브러리의 수가 아니라 실패했을 때 데이터와 사용자의 작업을
얼마나 안전하게 보존하는지에서 드러난다. bandi의 다음 과제도 새로운 기능을 무작정 늘리는
것이 아니라, 이미 만든 경계를 더 단단하게 만드는 일이다.
