# bandi 기능 정의서

> 문서 상태: 1차 구현 기준
> 작성 기준일: 2026-07-23

## 1. 서비스 목적

bandi는 학교 SSO로 확인된 연극 동아리 멤버가 팀 일정, 공식 안내, 자료, 활동
기록, 소품·장비와 멤버 권한을 한곳에서 운영하는 내부 서비스다.

신입 부원 모집은 기존 Google Form과 Sheets로 운영한다. 운영진은 선발된 사람의
학번과 이름을 사전 등록하고, 학교 SSO 인증 결과와 등록 정보를 연결한다.

## 2. 사용자와 권한

| 사용자 | 권한 |
| --- | --- |
| 미등록 학교 사용자 | 학교 인증 후 등록되지 않았음을 안내받는다. |
| `MEMBER` | 일정·공지·자료를 조회하고 본인 팀의 활동 기록을 사용한다. |
| `LEADER` | `MEMBER` 권한에 더해 소속 팀의 일정과 활동 기록을 관리한다. |
| `ADMIN` | 전체 팀의 일정, 공지·자료, 활동 기록, 소품·장비, 멤버와 권한을 관리한다. |

- 로컬 비밀번호 계정은 만들지 않는다.
- 휴학생과 졸업생은 로그인할 수 없다.
- 한 멤버는 현재 하나의 팀에만 소속된다.
- URL 역할 경계는 Spring Security가, 팀·대상·상태 권한은 Service가 검사한다.

## 3. 기능 범위

### F-01. 학교 SSO와 멤버 관리

- 운영진은 학번, 이름, 팀, 기수와 기본 역할을 사전 등록한다.
- 로그인 시 학교 인증 정보의 학번과 사전 등록 멤버를 연결한다.
- 운영진은 멤버의 팀·기수·역할·활동 상태와 변경 이력을 관리한다.
- 로그인 멤버는 내 프로필에서 이름·학번·기수·팀·역할과 SSO 확인 정보를 조회한다.
- 활성 멤버는 본인 팀을 즉시 변경할 수 있다. 팀장은 변경 전 현재 팀의 멤버만,
  운영진은 전체 멤버의 팀을 변경할 수 있으며, 모든 변경은 사유·이력·감사를 남긴다.
- 프로필 사진은 로그인한 멤버에게만 보이는 내부 아바타다. 사진을 교체하거나 삭제하면
  이전 원본을 보관하지 않고 퇴역 작업으로 완전 파기한다.
- 마지막 `ADMIN`의 권한 해제·비활성화는 허용하지 않는다.
- 회장은 `ADMIN`, `LEADER`, `MEMBER` 권한과 별개의 동아리 직책이다. 현재 회장은
  활성 멤버 한 명을 DB에서 지정하며, 회장 변경은 배포 없이 다음 문서 생성부터 반영한다.

### F-02. 홈

- 로그인 멤버에게 가까운 일정, 최신 공지와 자료, 확인이 필요한 활동 기록,
  소품·장비 현황을 요약한다.
- 홈은 별도 데이터를 저장하지 않고 각 feature의 읽기 모델을 조합한다.

### F-03. 통합 캘린더

- 전체와 팀 일정을 월·주·목록 보기로 조회한다. 데스크톱은 월간, 모바일은 주간
  목록을 기본으로 하며 사용자가 선택한 보기는 세션 동안 유지한다.
- 팀 필터는 DB의 실제 팀 이름을 사용한다. 특정 팀을 선택해도 동아리 전체 일정은
  함께 조회한다.
- `ADMIN`은 모든 일정을, `LEADER`는 소속 팀 일정을 등록·수정·삭제한다.
- 일정에는 제목, 선택 설명, 팀 범위, 시작·종료 시각, 선택 장소와 표시 색상을 기록한다.
  표시 색상은 네이비·민트·파랑·보라·주황·장미의 제한된 팔레트에서 고르며, 팀 범위와
  일정 제목을 대신하는 의미 체계로 사용하지 않는다.
- 종일 일정은 사용자가 마지막 날을 포함해 선택하고, 서버에는 시작일 00:00부터
  마지막 날 다음 날 00:00까지의 배타적 종료 구간으로 저장한다.
- 일정은 상세를 먼저 확인한 뒤 명시적으로 수정한다. 드래그 즉시 변경, 반복 일정,
  알림과 일정 상태는 1차 범위에 포함하지 않는다.

### F-04. 내부 공지

- 내부 공지는 전체 또는 팀별 멤버에게 전달한다.
- 내부 공지는 조회수 대신 멤버별 읽음 상태를 제공한다.
- 공지와 자료실은 서로 다른 화면과 URL로 운영한다. 공지는 목록, 상세, 작성, 수정
  화면을 분리하며, 짧은 작성 모달을 사용하지 않는다.
- 팀장은 본인 팀 공지만, 운영진은 전체·모든 팀 공지를 작성·수정·게시·종료·보관한다.
- 멤버용 `/notices`에는 게시 중인 공지의 중요 여부, 실제 대상 팀, 제목, 원 작성자,
  게시 시각과 본인 확인 상태를 표시한다. 팀장·운영진은 `/notices/manage`와
  `/notices/manage/{id}`에서 초안·예약·게시·종료·보관 공지를 별도로 관리한다.
- 본문은 GFM Markdown 원문으로 저장한다. 서버가 원시 HTML·스크립트·이벤트 속성·
  `javascript:` URL·HTTP 이미지를 제거한 결과만 멤버 화면에 렌더링한다. HTTPS 외부
  이미지는 직접 렌더링하며, 외부 제공자가 열람자의 접속 정보를 처리할 수 있음을 안내한다.
- 본문 이미지는 공지 전용 업로드에서 받은 `attachment://{storedFileId}` 참조만 허용한다.
  JPEG·PNG·WebP 파일은 각각 10MiB 이하이며, 저장 시 현재 공지의 첨부 목록에 실제로
  연결됐는지와 이미지 MIME·용량을 다시 검증한다. 일반 첨부는 다운로드로, 본문 이미지는
  공지 열람 권한을 통과한 inline 전송으로 제공한다.
- 본문 편집기에는 JPG·PNG·WebP 파일을 끌어놓아 내부 이미지로 올릴 수 있다. 외부 이미지는
  `![설명](https://...)` Markdown 문법으로만 추가하며, HTTP·data URL·원시 HTML 이미지는
  허용하지 않는다.
- 첨부 파일을 연결할 수 있으며, 기존 첨부는 수정자가 원래 업로더가 아니어도 유지한다.
  새로 연결하는 파일만 현재 수정자의 private 파일 소유권을 검증한다.
- 상태 전이는 `DRAFT → SCHEDULED/PUBLISHED → CLOSED → ARCHIVED`를 기본 흐름으로 한다.
  `SCHEDULED`와 `ARCHIVED`만 게시 시각·게시자를 초기화해 `DRAFT`로 되돌릴 수 있으며,
  재게시의 확인 상태가 섞이지 않도록 기존 읽음 기록도 초기화한다. `DRAFT`만 소프트
  삭제할 수 있고 게시 이력이 있는 공지는 삭제 대신 종료 후 보관한다.
- 읽음 현황은 게시 이력이 있는 공지의 관리 상세에서 대상 멤버 수와 멤버별 확인 시각을
  제공한다. 조회수·상태 변경 이력 테이블·본문 및 첨부 버전 이력·댓글·반응은 제공하지 않는다.
- 일반 공지와 공지 관리 목록은 20건 단위 서버 페이지네이션을 사용한다. 검색·읽음·대상·
  상태·팀 조건과 1부터 시작하는 현재 페이지를 URL에 보존한다.

### F-05. 자료실

- 자료는 전체 또는 특정 팀에 공개한다.
- 제목, 설명, 분류, 게시 상태와 파일 리비전을 관리한다.
- 파일은 권한 검증 후 다운로드한다.
- 공지 상태·작성 UI·읽음 상태는 자료실에 포함하지 않는다.
- 자료실 목록은 제목·설명·수정자, 분류와 공개 범위를 서버에서 검색하며 20건 단위 번호형
  페이지네이션을 사용한다.

### F-06. 활동 기록

- 팀은 네이비즘 인증 사진을 포함한 활동 기록을 작성한다.
- 운영진과 팀장은 범위에 맞는 기록을 검토하고 수정 요청 또는 승인한다.
- 파일 교체와 본문 변경은 이력으로 남긴다.
- 모든 로그인 멤버는 별도 `/activity-documents` 화면에서 기준 양식과 같은 HWPX 활동
  내역서를 임시 저장하거나 빈 양식을 내려받을 수 있다.
- HWPX 생성 입력은 대표자, 장소, 활동 일시, 사진 1장, 활동 내용과 참여자 1~14명이다.
  참여자 총계와 제목 월, 현재 회장 이름은 서버가 계산한다.
- 임시 저장하면 입력값은 활동 내역서 테이블에, 사진과 생성 HWPX는 활동 기록 파일로
  저장한다. 사용자는 저장한 초안을 수정해 HWPX를 다시 만들고 별도 행동으로 검수를
  요청한다. 운영진은 기존 활동 기록 검수 화면에서 사진과 HWPX를 내려받아 확인한다.
- 입력값과 파일을 브라우저 저장소나 오프라인 큐에는 남기지 않는다.
- 생성 결과는 반드시 `.hwpx`이며 PDF·DOCX·HWP로 대체하지 않는다.

### F-07. 소품·장비

- 수량형 품목과 개별 관리 장비를 구분해 관리한다.
- 품목명, 분류, 상태, 보관 위치, 소유 정보와 상태 변경 이력을 기록한다.
- 사진은 선택 사항이며 권한 검증 후 열람한다.

### F-08. 파일

- 바이너리는 `FILE_STORAGE_ROOT`의 `private/`, `public/` 아래에 저장한다.
- 업로드는 임시 파일 저장 뒤 원자적으로 이동한다.
- 공개용 파일은 원본을 유지한 채 별도 파일로 복사한다.
- 모든 파일은 서비스별 권한을 통과한 뒤 다운로드한다.
- 프로필 사진은 `PROFILE_IMAGE` 목적의 private 파일로만 저장한다. JPEG·PNG·WebP,
  최대 5MiB만 허용하며 일반 첨부와 교차 연결하지 않는다.
- 공지 본문 이미지는 일반 private 파일 메타데이터를 사용하되, 전용 업로드 경로와
  `notice/` 저장 키에서 JPEG·PNG·WebP, 최대 10MiB 검사를 통과한 파일만 허용한다.

## 4. 후속 범위

온보딩은 `member-onboarding-plan.md`의 별도 승인 이후 구현한다. 현재 1차
마이그레이션과 화면에는 온보딩 템플릿·진행 상태를 포함하지 않는다.

## 5. 공통 운영 원칙

- 사용자 입력과 파일명은 로그에 기록하지 않는다.
- 파일과 데이터 상태 변경은 CSRF 보호를 적용한다.
- 사용자 데이터는 JSP에서 `<c:out>`으로 출력하고, JavaScript는 `textContent`를
  사용한다.
- 상태 변경은 처리자와 시각을 감사할 수 있어야 한다.
