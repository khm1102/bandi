# bandi 기능 정의서

> 문서 상태: 1차 구현 기준
> 작성 기준일: 2026-07-23

## 1. 서비스 목적

bandi는 학교 SSO로 확인된 연극 동아리 멤버가 팀 일정, 공식 안내, 자료, 활동
기록, 소품·장비와 멤버 권한을 한곳에서 운영하는 내부 서비스다.

신입 부원 모집은 기존 Google Form과 Sheets로 운영한다. 운영진은 선발된 사람의
학번과 이름을 사전 등록하고, 학교 SSO 인증 결과와 등록 정보를 연결한다.

## 2. 사용자와 권한

| 사용자 | 권한 |
| --- | --- |
| 미등록 학교 사용자 | 학교 인증 후 등록되지 않았음을 안내받는다. |
| `MEMBER` | 일정·공지·자료를 조회하고 본인 팀의 활동 기록을 사용한다. |
| `LEADER` | `MEMBER` 권한에 더해 소속 팀의 일정과 활동 기록을 관리한다. |
| `ADMIN` | 전체 팀의 일정, 공지·자료, 활동 기록, 소품·장비, 멤버와 권한을 관리한다. |

- 로컬 비밀번호 계정은 만들지 않는다.
- 휴학생과 졸업생은 로그인할 수 없다.
- 한 멤버는 현재 하나의 팀에만 소속된다.
- URL 역할 경계는 Spring Security가, 팀·대상·상태 권한은 Service가 검사한다.

## 3. 기능 범위

### F-01. 학교 SSO와 멤버 관리

- 운영진은 학번, 이름, 팀, 기수와 기본 역할을 사전 등록한다. 기수는 `1-1`, `1-2`처럼
  이름만 가진 활성 기준정보이며, `ADMIN`이 새 기수를 추가한다.
- 로그인 시 학교 인증 정보의 학번과 사전 등록 멤버를 연결하고, 유효한 학과·학적·휴대폰 번호를
  최신 값으로 동기화한다. 휴대폰 번호가 없거나 형식이 맞지 않아도 로그인과 기존 저장 값은 유지한다.
- 학교 포털 계정 보호를 위해 최근 15분 안에 자격증명을 5회 틀리면 15분 동안 학교 SSO 요청을
  보내지 않는다. 성공한 학교 인증은 실패 상태를 즉시 지우며, 서버 장애·학적·멤버 연결 실패는
  실패 횟수에 포함하지 않는다. 학번 원문과 비밀번호는 실패 제한 저장소에 남기지 않는다.
- `ADMIN`은 전체 멤버의 팀·기수·역할·활동 상태와 변경 이력을 관리한다. `LEADER`는 현재
  소속 팀 멤버의 팀·기수만 변경할 수 있으며, 모든 변경은 사유·이력·감사를 남긴다.
- 로그인 멤버는 내 프로필에서 이름·학번·기수·팀·역할과 SSO 확인 정보를 조회한다. 휴대폰 번호는
  본인, `ADMIN`, 해당 팀 `LEADER`에게만 표시한다.
- 활성 멤버는 본인 팀을 즉시 변경할 수 있다. 팀장은 변경 전 현재 팀의 멤버만,
  운영진은 전체 멤버의 팀을 변경할 수 있으며, 모든 변경은 사유·이력·감사를 남긴다.
- 프로필 사진은 로그인한 멤버에게만 보이는 내부 아바타다. 사진을 교체하거나 삭제하면
  이전 원본을 보관하지 않고 퇴역 작업으로 완전 파기한다.
- 마지막 `ADMIN`의 권한 해제·비활성화는 허용하지 않는다. `WITHDRAWN` 멤버는 `ADMIN`이
  사유를 남겨 `ACTIVE`로 복구할 수 있으며, `REGISTRATION_CANCELLED`는 복구하지 않는다.
- 회장은 `ADMIN`, `LEADER`, `MEMBER` 권한과 별개의 동아리 직책이다. 현재 회장은
  활성 멤버 한 명을 DB에서 지정하며, 회장 변경은 배포 없이 다음 문서 생성부터 반영한다.

### F-02. 홈

- 로그인 멤버에게 가까운 일정, 최신 공지와 자료, 확인이 필요한 활동 기록,
  소품·장비 현황을 요약한다.
- 홈은 별도 데이터를 저장하지 않고 각 feature의 읽기 모델을 조합한다.

### F-03. 통합 캘린더

- 전체와 팀 일정을 월·주·목록 보기로 조회한다. 데스크톱은 월간, 모바일은 주간
  목록을 기본으로 하며 사용자가 선택한 보기는 세션 동안 유지한다.
- 팀 필터는 DB의 실제 팀 이름을 사용한다. 특정 팀을 선택해도 동아리 전체 일정은
  함께 조회한다.
- `ADMIN`은 모든 일정을, `LEADER`는 소속 팀 일정을 등록·수정·삭제한다.
- 일정에는 제목, 선택 설명, 팀 범위, 시작·종료 시각, 선택 장소와 표시 색상을 기록한다.
  표시 색상은 네이비·민트·파랑·보라·주황·장미의 제한된 팔레트에서 고르며, 팀 범위와
  일정 제목을 대신하는 의미 체계로 사용하지 않는다.
- 종일 일정은 사용자가 마지막 날을 포함해 선택하고, 서버에는 시작일 00:00부터
  마지막 날 다음 날 00:00까지의 배타적 종료 구간으로 저장한다.
- 일정은 상세를 먼저 확인한 뒤 명시적으로 수정한다. 드래그 즉시 변경, 반복 일정,
  알림과 일정 상태는 1차 범위에 포함하지 않는다.

### F-04. 내부 공지

- 내부 공지는 전체 또는 팀별 멤버에게 전달한다.
- 내부 공지는 조회수 대신 멤버별 읽음 상태를 제공한다.
- 공지와 자료실은 서로 다른 화면과 URL로 운영한다. 공지는 목록, 상세, 작성, 수정
  화면을 분리하며, 짧은 작성 모달을 사용하지 않는다.
- 팀장은 본인 팀 공지만, 운영진은 전체·모든 팀 공지를 작성·수정·게시·종료·보관한다.
- 멤버용 `/notices`에는 게시 중인 공지의 중요 여부, 실제 대상 팀, 제목, 원 작성자,
  게시 시각과 본인 확인 상태를 표시한다. 팀장·운영진은 `/notices/manage`와
  `/notices/manage/{id}`에서 초안·예약·게시·종료·보관 공지를 별도로 관리한다.
- 본문은 GFM Markdown 원문으로 저장한다. 서버가 원시 HTML·스크립트·이벤트 속성·
  `javascript:` URL·HTTP 이미지를 제거한 결과만 멤버 화면에 렌더링한다. HTTPS 외부
  이미지는 직접 렌더링하며, 외부 제공자가 열람자의 접속 정보를 처리할 수 있음을 안내한다.
- 본문 이미지는 공지 전용 업로드에서 받은 `attachment://{storedFileId}` 참조만 허용한다.
  JPEG·PNG·WebP 파일은 각각 10MiB 이하이며, 저장 시 현재 공지의 첨부 목록에 실제로
  연결됐는지와 이미지 MIME·용량을 다시 검증한다. 일반 첨부는 다운로드로, 본문 이미지는
  공지 열람 권한을 통과한 inline 전송으로 제공한다.
- 본문 편집기에는 JPG·PNG·WebP 파일을 끌어놓아 내부 이미지로 올릴 수 있다. 외부 이미지는
  `![설명](https://...)` Markdown 문법으로만 추가하며, HTTP·data URL·원시 HTML 이미지는
  허용하지 않는다.
- 첨부 파일을 연결할 수 있으며, 기존 첨부는 수정자가 원래 업로더가 아니어도 유지한다.
  새로 연결하는 파일만 현재 수정자의 private 파일 소유권을 검증한다.
- 상태 전이는 `DRAFT → SCHEDULED/PUBLISHED → CLOSED → ARCHIVED`를 기본 흐름으로 한다.
  `SCHEDULED`와 `ARCHIVED`만 게시 시각·게시자를 초기화해 `DRAFT`로 되돌릴 수 있으며,
  재게시의 확인 상태가 섞이지 않도록 기존 읽음 기록도 초기화한다. `DRAFT`만 소프트
  삭제할 수 있고 게시 이력이 있는 공지는 삭제 대신 종료 후 보관한다.
- 읽음 현황은 게시 이력이 있는 공지의 관리 상세에서 대상 멤버 수와 멤버별 확인 시각을
  제공한다. 조회수·상태 변경 이력 테이블·본문 및 첨부 버전 이력·댓글·반응은 제공하지 않는다.
- 일반 공지와 공지 관리 목록은 20건 단위 서버 페이지네이션을 사용한다. 검색·읽음·대상·
  상태·팀 조건과 1부터 시작하는 현재 페이지를 URL에 보존한다.
- 모든 로그인 멤버는 공지 상세의 `공유`로 기존 인증 URL을 공유할 수 있다. 원 작성자·
  해당 팀 공지 관리 권한자·`ADMIN`은 제목 공개 공유 링크를 발급·중단할 수 있다. 제목 공개
  링크는 비로그인에게 제목과 로그인 안내만 보이고, 로그인 후에는 기존 공지 권한 검사를
  통과한 상세로 이동한다. 본문·작성자·팀·첨부는 공유 페이지와 Open Graph에 공개하지 않는다.

### F-05. 자료실

- 자료는 모든 활성 멤버가 함께 쓰는 내부 게시판이다. 제목, GFM Markdown 본문과 여러 첨부
  파일만 관리하며 팀 범위·분류·상단 고정·게시 상태·초안·보관·파일 리비전은 제공하지 않는다.
- 모든 활성 멤버가 작성·열람할 수 있고, 원 작성자와 `ADMIN`만 수정·소프트 삭제할 수 있다.
  `LEADER` 권한만으로 다른 사람의 자료를 관리할 수 없다.
- 본문 이미지는 자료 첨부로 검증된 `attachment://{storedFileId}` 내부 참조만 허용한다.
  외부 이미지와 iframe은 렌더링하지 않는다. 첨부와 본문 이미지는 자료 열람 권한을 확인한
  Spring Boot inline/download 전송으로 제공한다.
- 본문에서 단독 줄로 작성한 HTTPS URL은 서버가 안전하게 수집한 Open Graph 스냅샷으로 링크
  카드를 표시한다. 수집할 수 없거나 5개를 넘는 URL은 일반 안전 링크로 남긴다. 열람자의
  브라우저는 외부 메타데이터·대표 이미지를 직접 요청하지 않는다.
- 자료실 목록은 제목·본문·작성자 검색과 20건 단위 서버 페이지네이션을 사용한다. 목록은
  미디어 카드로 제목·본문 요약·작성자·수정 시각·첨부 수를 보여 주고, 상세·작성·수정은
  각각 전용 URL로 제공한다.
- 모든 로그인 멤버는 자료 상세의 `공유`로 인증 URL을 공유할 수 있다. 원 작성자와 `ADMIN`은
  제목 공개 공유 링크를 발급·중단할 수 있다. 비로그인 공유 페이지의 공개 범위는 제목과
  로그인 안내로 한정하며, 로그인 후 원래 자료 상세의 기존 권한 검사를 적용한다.

### F-06. 활동 기록

- `/activity`는 로그인 멤버의 **내 활동 기록**이다. 간단 활동 기록과 HWPX 활동 내역서는
  하나의 활동 기록·검수 흐름으로 관리한다.
- 간단 활동 기록은 제목·일시·참여 인원·내용을 필수로 하고 사진은 선택 사항이다.
  HWPX 활동 내역서는 생성된 HWPX와 네이비즘 인증 사진이 모두 있어야 제출할 수 있다.
- 상태는 `DRAFT → SUBMITTED → TEAM_APPROVED → APPROVED → ARCHIVED`이며,
  팀장 또는 관리자의 보완 요청은 `REVISION_REQUESTED`로 관리한다. 보완 후 다시 제출하면
  `SUBMITTED`로 돌아가 팀장 승인을 다시 받아야 한다.
- 팀장은 자기 팀의 `SUBMITTED` 기록만 1차 승인 또는 보완 요청할 수 있다. 관리자는
  `TEAM_APPROVED` 기록을 최종 승인하고, 긴급 상황에서는 사유를 남겨 `SUBMITTED`를 직접
  최종 승인할 수 있다. 팀장은 자신의 기록을 1차 검수·보완 요청할 수 없지만, 관리자는
  본인이 작성한 기록도 최종 검수·보관할 수 있다.
- `/activity/review`는 팀장·관리자 검수 화면이며, 관리자는 필터 전체 기준 CSV를 내려받을 수
  있다. CSV에는 본문·사진·학번을 넣지 않는다.
- `/activity/archive`는 모든 로그인 멤버가 최종 승인된 전체 기록과 HWPX를 열람하는 화면이다.
- 파일 교체와 본문 변경, 상태 전이는 이력으로 남긴다.
- 모든 로그인 멤버는 별도 `/activity-documents` 화면에서 기준 양식과 같은 HWPX 활동
  내역서를 임시 저장하거나 빈 양식을 내려받을 수 있다.
- HWPX 생성 입력은 목록에서 구분할 활동 기록 제목, 대표자, 장소, 활동 일시, 사진 1장,
  활동 내용과 참여자 1~14명이다. 참여자 총계와 HWPX 양식 제목의 월, 현재 회장 이름은
  서버가 계산한다. 활동 기록 제목은 HWPX 양식 제목 형식에 영향을 주지 않는다.
- 임시 저장하면 입력값은 활동 내역서 테이블에, 사진과 생성 HWPX는 활동 기록 파일로
  저장한다. 사용자는 저장한 초안을 수정해 HWPX를 다시 만들고 별도 행동으로 검수를
  요청한다. 운영진은 기존 활동 기록 검수 화면에서 사진과 HWPX를 내려받아 확인한다.
- 입력값과 파일을 브라우저 저장소나 오프라인 큐에는 남기지 않는다.
- 생성 결과는 반드시 `.hwpx`이며 PDF·DOCX·HWP로 대체하지 않는다.

### F-07. 소품·장비

- 수량형 품목과 개별 관리 장비를 구분해 관리한다.
- 품목명, 분류, 상태, 보관 위치, 소유 정보와 상태 변경 이력을 기록한다.
- 사진은 선택 사항이며 권한 검증 후 열람한다. 바이너리는 로컬 파일 저장소에 두고
  `stored_file` 메타데이터와 품목의 사진 연결만 DB에 저장한다.
- 목록은 품목명·분류·상태·관리 방식 검색 조건과 20건 단위 서버 페이지네이션을 사용한다.
  데스크톱은 사진 썸네일 행 목록, 모바일은 사진·상태·수량·위치를 우선한 카드 목록으로
  제공한다.
- 등록과 수정은 전용 페이지에서 처리한다. 모바일 파일 입력은 카메라 촬영 힌트와 앨범 선택을
  제공하며, 선택한 사진은 저장 전 즉시 미리보기하고 교체할 수 있다.
- `ADMIN`만 품목을 등록·수정·소프트 삭제·복구한다. 삭제된 품목은 일반 목록·상세·사진
  다운로드에서 제외하고, 관리자의 삭제됨 목록에서만 복구할 수 있다. 개별 장비와 상태 이력은
  삭제·복구에도 보존한다.

### F-08. 파일

- 바이너리는 `FILE_STORAGE_ROOT`의 `private/`, `public/` 아래에 저장한다.
- 업로드는 임시 파일 저장 뒤 원자적으로 이동한다.
- 공개용 파일은 원본을 유지한 채 별도 파일로 복사한다.
- 모든 파일은 서비스별 권한을 통과한 뒤 다운로드한다.
- 프로필 사진은 `PROFILE_IMAGE` 목적의 private 파일로만 저장한다. JPEG·PNG·WebP,
  최대 5MiB만 허용하며 일반 첨부와 교차 연결하지 않는다.
- 공지 본문 이미지는 일반 private 파일 메타데이터를 사용하되, 전용 업로드 경로와
  `notice/` 저장 키에서 JPEG·PNG·WebP, 최대 10MiB 검사를 통과한 파일만 허용한다.

## 4. 후속 범위

온보딩 템플릿·진행 상태는 `member-onboarding-plan.md`의 별도 승인 이후 구현한다. 현재 1차
마이그레이션과 화면에는 템플릿·배정·단계 진행 상태를 포함하지 않는다. 다만 로그인 멤버가
동아리 기본 안내와 사이트 사용 방법을 확인하는 정적 `/onboarding` 안내 화면은 제공하며,
완료 여부·입력값·진행 상태를 저장하지 않는다.

## 5. 공통 운영 원칙

- 반디는 지원 브라우저에서 설치형 웹 앱으로 실행할 수 있다. 설치는 현재 로그인·세션·권한
  정책을 그대로 사용하며, `start_url`은 홈(`/dashboard`)이다.
- 서비스 워커는 네트워크 전용으로 요청을 전달한다. API 응답·화면·파일·사용자 입력을
  오프라인 캐시나 브라우저 저장소에 보관하지 않으며, 오프라인에서는 기존과 같이 이용할 수 없다.
- 설치형 모바일 화면도 브라우저 화면과 같은 반응형 레이아웃을 사용한다. 가상 키보드가 열릴 때는
  viewport 높이를 다시 계산해 입력 영역과 주요 행동이 가려지지 않게 한다.
- 사용자 입력과 파일명은 로그에 기록하지 않는다.
- 파일과 데이터 상태 변경은 CSRF 보호를 적용한다.
- 사용자 데이터는 JSP에서 `<c:out>`으로 출력하고, JavaScript는 `textContent`를
  사용한다.
- 상태 변경은 처리자와 시각을 감사할 수 있어야 한다.
