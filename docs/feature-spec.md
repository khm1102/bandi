## 1. 서비스 목적

bandi는 연극 동아리 구성원이 팀 일정, 활동 인증, 공시·자료와 멤버 권한을 한곳에서 관리하는 내부 운영 서비스다.

내부 사용자는 학교 계정 인증을 거쳐 접속한다. 신입 부원 모집 접수는 기존 Google Form을 유지하고, 운영진이 선발된 지원자의 기본 정보를 bandi에 수동 등록한다.

## 3. 사용자와 권한

### 3.1 사용자 유형

| 사용자 | 설명 |
|---|---|
| 외부 관람객 | 공개 공시와 공연 정보를 조회하고 관람을 신청하는 비로그인 사용자 |
| 미등록 학교 사용자 | 학교 인증은 성공했지만 bandi 멤버로 등록되지 않은 사용자 |
| 일반 부원 | 본인과 소속 팀의 운영 정보를 사용하는 활성 멤버 |
| 팀장 | 일반 부원 권한에 더해 소속 팀의 일정과 활동 기록을 관리하는 멤버 |
| 운영진 | 전체 팀, 회비, 멤버와 권한을 관리하는 멤버 |

### 3.2 권한 원칙

- 학교 인증 성공 여부와 동아리 서비스 이용 권한은 분리한다.
- 학교 인증에 성공해도 활성 멤버로 등록되지 않은 사용자는 내부 기능을 사용할 수 없다.
- 일반 부원은 전체 일정 조회와 본인 관련 출석·회비 조회가 가능하다.
- 팀장은 소속 팀의 일정과 활동 기록을 등록·수정·삭제할 수 있다.
- 운영진은 모든 팀의 일정과 활동 기록, 공시·공지·자료실, 제작 업무, 공연 운영, 행사 출석, 회비, 멤버와 권한을 관리할 수 있다.
- 화면에서 버튼을 숨기는 것과 별개로 서버에서 권한을 다시 검증해야 한다.
- 권한 변경, 멤버 비활성화, 회비 처리처럼 영향이 큰 작업은 처리자와 처리 시각을 기록한다.

### 3.3 권한 세부 정책

- 일반 부원과 팀장은 통합 캘린더에서 모든 팀 일정을 조회할 수 있다.
- 팀장은 소속 팀의 일정과 활동 기록을 생성·수정·검수할 수 있다. 다른 팀 일정은 조회할 수 있지만 다른 팀 활동 기록은 조회·수정할 수 없다.
- 운영진과 회장을 별도 시스템 역할로 구분하지 않고 모두 `ADMIN`으로 관리한다. 회장·총무 같은 직책 표시는 권한과 분리된 프로필 정보로 확장할 수 있다.
- 마지막 `ADMIN`의 권한 해제·비활성화·탈퇴는 금지한다.
- `ADMIN` 본인의 권한 하향은 다른 `ADMIN`만 처리할 수 있다.
- 모든 권한·팀 변경은 사유, 처리자와 처리 시각을 이력으로 남긴다.

## 4. 기능 상세

### F-01. 학교 계정 인증

#### 목적

학교 계정을 이용해 사용자의 학적 신원을 확인하고, bandi에 등록된 멤버와 연결한다.

#### 기본 흐름

1. 사용자가 학교 포털 학번과 비밀번호를 입력한다.
2. 제공된 Python PoC의 로그인 흐름으로 학교 포털 인증을 수행한다.
3. 포털 정보 조회 흐름으로 학번, 이름, 학적 상태와 학과를 확인한다.
4. 학적 상태가 `재학생`이 아니면 로그인을 거부한다.
5. 재학생이면 학번을 기준으로 bandi 멤버 등록 정보와 대조한다.
6. `SSO 연결 대기` 멤버이고 등록 정보가 일치하면 SSO 연결 상태를 `LINKED`, 멤버 상태를 `ACTIVE`로 전환한다.
7. 활성 멤버라면 일반 bandi 로그인 세션을 생성한다. 온보딩을 구현하기 전까지 별도의 제한 세션이나 온보딩 이동은 사용하지 않는다.
8. 등록되지 않았거나 활동 중지·탈퇴 상태인 멤버라면 내부 화면 접근을 차단하고 안내한다.

#### 식별 정보

- 1차 매칭 키는 학번으로 한다.
- 이름은 표시 및 대조용으로 사용하며 고유 식별자로 사용하지 않는다.
- 학교 학적 상태는 로그인 허용 여부 판단에 사용하고 학과는 멤버 정보 대조용으로 사용한다.
- 이메일, 전화번호, 주소와 포털 로그인 이력은 서비스 목적에 필요하지 않으면 수집하지 않는다.

#### 확정 인증 방식

- 제공된 `tukorea_login.py`와 `portal_info.py` PoC의 세션 생성, 동적 키 획득, AES 암호화, 로그인 성공 판정과 포털 정보 추출 로직을 프로토콜 정본으로 사용한다.
- 운영 요청 경로에서 Python 프로세스를 매번 실행하지 않는다. PoC의 요청 순서와 판정 규칙을 `SchoolSsoClient` 경계 안의 Java 구현으로 옮기고, PoC는 회귀 비교와 학교 페이지 변경 분석용 기준 자료로 보존한다.
- Controller와 멤버 Service는 학교 HTML·쿠키·암호화 세부사항을 알지 않으며 인증 어댑터의 정규화된 결과만 사용한다.
- 학교 비밀번호는 인증 요청 처리 중에만 사용하고 저장, 캐시, 로그 또는 DB에 남기지 않는다.
- 학교 인증 세션 쿠키와 응답 원문을 애플리케이션 로그에 남기지 않는다.
- PoC가 반환할 수 있는 원문 응답, 세션 식별자와 불필요한 개인정보는 bandi 계층으로 전달하거나 저장하지 않는다.
- 인증 실패, 학교 시스템 장애, 응답 형식 변경을 구분해 사용자에게 안내한다.
- 학교 로그인 페이지 구조나 암호화 방식이 변경되면 인증이 중단될 수 있음을 운영 정책에 반영한다.

#### 학적 상태 정책

- 정규화한 학적 상태가 정확히 `재학생`인 경우에만 로그인할 수 있다.
- 휴학생과 졸업생은 bandi 멤버로 등록돼 있어도 로그인할 수 없다.
- 학적 상태가 누락됐거나 알 수 없는 값이면 허용하지 않고 운영진 문의를 안내한다.
- 로그인할 때마다 학교 학적 상태를 다시 확인해 이전 세션이나 DB 값만으로 허용하지 않는다.
- 학교 학적 상태와 동아리의 `활성`, `활동 중지`, `탈퇴` 상태는 별도로 관리하며 두 조건을 모두 통과해야 한다.

#### 예외 상황

| 상황 | 처리 정책 |
|---|---|
| 학교 인증 실패 | 자격증명을 다시 확인하도록 안내한다. |
| 학교 시스템 장애·시간 초과 | 잠시 후 다시 시도하도록 안내하고 내부 오류와 구분한다. |
| 학교 인증 성공·멤버 미등록 | 운영진에게 등록을 요청하도록 안내한다. |
| 학교 인증 성공·SSO 연결 대기 | 등록 정보를 대조하고 이상이 없으면 계정을 연결·활성화한 뒤 홈으로 이동한다. |
| 학교 인증 성공·휴학생 또는 졸업생 | 로그인하지 않고 재학생만 이용할 수 있음을 안내한다. |
| 학교 인증 성공·학적 상태 확인 불가 | 기본 거부하고 운영진 문의를 안내한다. |
| 멤버 비활성·탈퇴 상태 | 로그인하지 않고 운영진 문의를 안내한다. |
| 등록 이름과 학교 이름 불일치 | 학번을 기준으로 식별하되 운영진 확인 대상으로 표시한다. |

#### 구현 전 확인

- 비공식 포털 인증 사용의 학교 이용약관, 개인정보 처리와 운영상 허용 여부를 확인한다.
- PoC 실행 방식, 장애 격리, 타임아웃과 학교 화면 변경 감지 방법을 기술 설계에서 확정한다.

### F-02. 홈

#### 목적

로그인한 사용자가 당장 확인해야 할 동아리 운영 정보를 한 화면에서 요약한다.

#### 공통 표시 후보

- 오늘 및 가까운 예정 일정
- 오늘 또는 가까운 행사의 출석 확인 상태
- 최근 또는 중요 내부 공지
- 최근 등록된 팀 활동 기록
- 본인의 미납 회비 항목

#### 운영진 추가 표시 후보

- 진행 중이거나 종료된 행사의 출석 처리 현황
- 팀별 최근 활동 기록 제출 현황
- 전체 회비 미납 인원과 미수납액
- SSO 연결 대기 또는 등록 대기 멤버 수

#### 정책

- 홈은 별도 업무 데이터를 생성하지 않고 각 기능의 데이터를 집계한다.
- 사용자 역할과 소속 팀에 따라 카드와 바로가기를 다르게 노출한다.
- 제거된 일정 조율과 커뮤니티 게시판 정보는 홈에 표시하지 않는다.
- 기존 커뮤니티의 최근 게시글 영역은 중요 공지 또는 최근 공지 영역으로 교체한다.
- 외부 공시는 내부 홈의 필수 요약 대상이 아니며 필요할 때 별도 바로가기로 제공한다.

#### 논의 필요

- 홈에 반드시 보여야 하는 지표와 표시 순서를 역할별로 확정한다.
- 최근 활동 기록의 기준 기간과 노출 건수를 정한다.

### F-03. 통합 캘린더

#### 목적

전체 동아리와 팀별 일정을 월간 캘린더에서 확인하고 관리한다.

#### 조회 기능

- 전체 팀 일정을 월 단위로 조회한다.
- 팀별 필터를 제공한다.
- 일정명, 담당 팀, 시작·종료 일시, 장소와 설명을 표시한다.
- 날짜를 선택하면 해당 날짜의 일정 목록과 상세 정보를 표시한다.
- 이전 달과 다음 달로 이동한다.

#### 관리 기능

- 팀장은 소속 팀 일정을 등록·수정·삭제한다.
- 운영진은 모든 팀 일정을 등록·수정·삭제한다.
- 삭제 전 확인 절차를 제공한다.
- 등록자, 최종 수정자와 수정 시각을 기록한다.

#### 일정 필수값

- 일정명
- 담당 팀 또는 전체 일정 여부
- 시작 일시
- 종료 일시 또는 종일 여부
- 장소
- 설명

#### 검증 규칙

- 종료 시각은 시작 시각보다 빠를 수 없다.
- 삭제되거나 비활성화된 팀에는 새 일정을 등록할 수 없다.
- 팀장은 요청에서 임의로 다른 팀을 지정할 수 없다.

#### 논의 필요

- 반복 일정이 필요한지 결정한다.
- 행사 일정을 캘린더에서 어떤 방식으로 표시할지 결정한다.
- 일정 알림을 1차 범위에 포함할지 결정한다.

### F-04. 활동 기록

#### 목적

팀별 활동을 인증 사진과 설명으로 기록하고, 운영진이 전체 팀의 활동 현황을 확인한다.

#### 범위

- 활동 기록은 자료실과 분리한다.
- 활동 기록은 일반 문서 공유가 아니라 네이비즘을 이용한 팀 활동 인증을 목적으로 한다.
- 기록은 반드시 하나의 팀에 소속된다.

#### 작성 항목

- 담당 팀
- 활동 일자와 시간
- 활동 제목 또는 활동 유형
- 활동 내용
- 참여 멤버 또는 참여 인원
- 활동 참여자와 네이비즘 시각 화면이 함께 확인되는 인증 사진
- 필요 시 추가 활동 사진
- 작성자와 작성 시각

#### 권한

- 일반 부원은 전체 팀 기록을 조회하고 소속 팀 기록을 작성할 수 있다.
- 팀장은 소속 팀 기록을 작성·수정·삭제한다.
- 운영진은 모든 팀 기록을 작성·수정·삭제하고 검수할 수 있다.

#### 인증 사진 정책

- 이미지 파일만 업로드할 수 있다.
- 인증 사진에는 실제 활동 참여자와 네이비즘 시각 화면이 한 화면 안에서 식별 가능하게 포함돼야 한다.
- 네이비즘 API 연동이나 자동 판정 대신 사용자가 촬영한 사진을 증빙으로 제출한다.
- 허용 확장자, MIME 타입, 최대 용량과 최대 개수를 제한한다.
- 원본 파일명과 실제 저장소 키를 분리한다.
- 인증 사진 교체와 기록 수정 이력을 남긴다.
- 사진만으로 자동 인증하지 않고, 1차 버전에서는 운영진 육안 확인을 기본으로 한다.
- 자동 OCR이나 촬영 시각 판독은 별도 기능으로 검토한다.

#### 검수 상태 후보

- `작성 중`
- `제출`
- `승인`
- `보완 요청`

#### 논의 필요

- 운영진 승인 전에도 다른 부원이 기록을 볼 수 있는지 결정한다.
- 참여 멤버를 직접 선택할지 인원수만 입력할지 결정한다.

### F-05. 공시 게시판

#### 목적

운영진이 모집, 공연과 대외 활동에 관한 공식 정보를 게시하고 외부 사용자와 멤버가 확인하게 한다.

공시는 자유 글, 질문, 댓글과 좋아요를 제공하는 커뮤니티 게시판과 별개의 기능이다.

#### 조회 기능

- 로그인하지 않은 외부 사용자와 멤버가 게시된 공시 목록과 상세 내용을 조회한다.
- 중요 공시를 목록 상단에 고정한다.
- 제목과 본문을 기준으로 검색한다.
- 최신순과 중요 공시 우선순으로 정렬한다.
- 공시 제목, 본문, 작성자, 게시 시각과 최종 수정 시각을 표시한다.
- 필요하면 첨부파일을 조회하고 다운로드한다.

#### 관리 기능

- 운영진은 공시를 작성·수정·게시 종료한다.
- 작성 중인 공시는 임시 저장할 수 있다.
- 게시 시작 시각과 게시 종료 시각을 지정할 수 있다.
- 중요 공시 여부를 설정한다.
- 게시된 공시를 수정하면 수정 시각과 수정자를 기록한다.
- 이미 게시된 공시는 물리 삭제하지 않고 게시 종료 또는 보관 상태로 변경한다.

#### 상태 후보

- `임시 저장`
- `게시 중`
- `게시 종료`
- `보관`

#### 제외 범위

- 일반 부원의 글 작성
- 댓글과 답글
- 좋아요와 추천
- 자유 게시판과 질문 게시판
- 실시간 채팅

#### 논의 필요

- 모집, 공연, 결과 안내 외에 어떤 공시 카테고리를 제공할지 결정한다.
- 첨부파일을 1차 범위에 포함할지 결정한다.
- 공시 게시 또는 수정 시 알림을 발송할지 결정한다.

### F-06. 공지·자료실

#### 목적

내부 공지와 업무 자료를 한 정보 허브에서 제공한다. 공지와 자료는 같은 탐색 구조를 사용하되 서로 다른 데이터와 권한으로 관리한다.

#### 조회 기능

- 활성 멤버만 공지 목록과 상세 내용을 조회한다.
- 전체 공지와 본인 소속 팀 공지를 구분한다.
- 중요 공지를 상단에 고정한다.
- 공지 대상, 제목, 본문, 작성자, 게시 시각과 수정 시각을 표시한다.
- 홈에 최근 또는 중요 공지를 요약한다.

#### 읽음 확인

- 조회수 숫자는 제공하지 않는다.
- 멤버가 공지 상세를 처음 열었을 때 공지와 멤버 조합의 읽음 기록과 최초 확인 시각을 저장한다.
- 운영진은 전체 공지의 확인·미확인 멤버 명단을 조회한다.
- 팀장은 소속 팀 공지의 확인·미확인 멤버 명단만 조회한다.
- 공시 게시판은 비로그인 사용자가 읽을 수 있으므로 개인별 읽음 기록 대상이 아니다.

#### 자료실 기능

- 자료는 전체 동아리 또는 특정 팀 범위로 등록한다.
- 제목, 설명, 분류, 첨부파일, 작성자와 등록·수정 시각을 제공한다.
- 활성 멤버는 전체 자료와 본인 소속 팀 자료를 검색·조회·다운로드한다.
- 운영진은 모든 자료를 등록·수정·보관하고, 팀장은 소속 팀 자료를 관리한다.
- 일반 부원은 자료를 조회하고 다운로드하며 1차 범위에서는 등록하지 않는다.
- 파일 교체 이력과 업로더를 기록하고, 자료를 삭제하기보다 보관 상태로 전환한다.

#### 관리 기능

- 운영진은 전체 공지와 모든 팀 공지를 관리한다.
- 팀장은 소속 팀 공지를 작성·수정·게시 종료한다.
- 일반 부원은 공지를 작성하지 않는다.
- 댓글, 좋아요와 자유 글은 제공하지 않는다.
- 공지를 물리 삭제하기보다 게시 종료 또는 보관 상태로 변경한다.

#### 논의 필요

- 중요 공지 알림을 어떤 채널로 발송할지 결정한다.
- 공지 본문에도 첨부파일을 허용할지, 모든 파일을 자료실 항목으로 연결할지 결정한다.

### F-07. 신입 부원 모집

#### 현행 프로세스

1. 지원자가 Google Form으로 지원 내용을 제출한다.
2. 응답이 Google Sheets에 저장된다.
3. 운영진이 지원 내용을 검토하고 선발한다.
4. 선발된 인원을 bandi 멤버로 등록한다.

#### 확정 방식: 관리자 수동 등록

- 운영진은 기존 Google Sheets를 직접 확인한다.
- 합격자의 학번, 이름, 팀, 기수만 bandi에 입력한다.
- 등록된 멤버는 `SSO 연결 대기` 상태가 된다.
- 해당 학번 사용자가 처음 학교 인증에 성공하면 계정과 멤버를 연결한다.
- 운영진은 등록 대기 멤버를 수정하거나 등록 취소할 수 있다.
- 지원서 원본과 선발 결과는 기존 Google Form과 Sheets에서 관리한다.
- bandi는 지원서 전체 내용과 불합격자 정보를 저장하지 않는다.
- Google Sheets API는 1차 범위에서 연동하지 않는다.

#### 추후 검토

- 수동 입력량과 입력 오류가 운영상 문제가 되면 Google Sheets 읽기 전용 연동을 다시 검토한다.
- 연동을 추가하더라도 Google Sheets를 지원서 원본 데이터의 기준으로 유지한다.
- 양방향 수정과 지원서 전체 내용 복제는 별도 요구사항이 확정되기 전까지 제외한다.

### F-08. 신입 부원 온보딩

> 구현 상태: 후속. 아래 내용은 삭제하지 않고 별도 온보딩 작업의 출발점으로 보존하며, 현재 1차 구현의 화면·API·테이블 범위에는 포함하지 않는다.

#### 목적

사전 등록된 신입 부원이 첫 학교 인증 후 본인의 소속을 확인하고, 필수 동의와 동아리·팀 안내를 거쳐 실제 활동을 시작하게 한다.

#### 기본 흐름

1. 운영진이 합격자의 학번, 이름, 기수와 팀을 사전 등록한다.
2. 신입 부원이 처음 학교 인증을 진행한다.
3. 인증 학번과 사전 등록 멤버를 연결한다.
4. 신입 부원이 이름, 기수, 팀과 역할을 확인한다.
5. 개인정보 처리와 필수 운영 규칙을 확인한다.
6. 동아리 공통 안내와 팀별 안내를 확인한다.
7. 초기 체크리스트를 완료하고 홈으로 이동한다.

#### 후속 접근 정책

- 소속 정보 확인과 필수 동의 전에는 온보딩 화면과 로그아웃만 허용한다.
- 필수 단계를 완료하면 일반 기능 접근을 허용한다.
- 공통 안내와 팀별 체크리스트가 남아 있으면 홈에 진행 카드를 표시한다.
- 정보 불일치가 발생하면 사용자가 직접 소속을 바꾸지 않고 운영진에게 정정을 요청한다.
- 중간에 종료한 경우 마지막 미완료 단계부터 이어서 진행한다.

#### 운영진 기능

- `SSO 연결 대기`, `진행 중`, `확인 필요`, `완료`, `등록 취소` 상태별 멤버를 조회한다.
- 멤버별 마지막 완료 단계와 마지막 진행 시각을 확인한다.
- 팀·기수 정보 정정과 잘못된 계정 연결을 처리한다.
- 기본 제공 템플릿을 복제해 기수별 온보딩 템플릿을 만들고 단계의 제목, 내용, 순서, 필수 여부와 적용 팀을 편집한다.
- 템플릿은 초안, 게시, 보관 상태로 관리하고 게시 버전을 멤버에게 배정한다.
- 이미 진행 중인 멤버의 단계가 예고 없이 바뀌지 않도록 배정 시점의 게시 버전을 유지한다.

#### 상세 기획

단계별 화면, 체크리스트, 예외 처리와 데이터 설계는 후속 정본인 [`member-onboarding-plan.md`](member-onboarding-plan.md)를 따른다.

### F-09. 행사·출석 관리

#### 목적

회식, MT, 총회와 같은 동아리 행사와 실제 출석 결과를 관리한다. 참석 의사 투표는 제공하지 않는다.

#### 행사 생성

- 운영진은 행사명, 설명, 장소, 시작·종료 일시와 출석 확인 가능 시간을 입력한다.
- 필요하면 전체 멤버, 특정 팀 또는 선택한 멤버를 참석 대상으로 지정한다.
- 팀장에게 소속 팀 행사 생성 권한을 줄지는 별도로 결정한다.

#### 출석 처리

- 출석은 행사와 대상 멤버의 실제 참석 결과로 기록한다.
- 출석 상태는 최소 `출석`, `지각`, `결석`, `인정 결석`으로 구분한다.
- 운영진은 현장에서 출석을 일괄 또는 개별 처리하고 필요한 경우 사유를 기록한다.
- 출석 상태를 수정하면 이전 값, 변경자와 변경 시각을 이력으로 남긴다.

멤버 본인 체크인 허용 여부와 QR·일회용 코드·단순 버튼 중 어떤 방식을 사용할지는 아직 확정하지 않았다. 확정 전 1차 데이터 설계는 운영진이 출석 결과를 처리하는 흐름만 전제로 한다.

#### 운영진 조회

- 행사별 대상 인원과 출석 상태별 인원수를 표시한다.
- 상태별 멤버 명단과 처리 시각을 조회한다.
- 출석 확인 시간을 종료하거나 필요한 경우 다시 열 수 있다.
- 멤버별 행사 출석 이력을 조회한다.

#### 논의 필요

- 팀장에게 행사 생성 권한을 줄 것인가?
- 멤버 본인 체크인을 허용할지, 운영진 처리만 허용할지 결정한다.
- 현장 체크인 방식으로 QR, 일회용 코드 또는 단순 버튼 중 무엇을 사용할지 결정한다.

### F-10. 회비

#### 목적

멤버는 본인의 회비 납부 현황을 확인하고, 운영진은 회비 항목과 멤버별 수납 상태를 관리한다.

#### 멤버 기능

- 본인에게 부과된 회비 항목을 조회한다.
- 항목명, 금액, 기준 기간, 납부 기한, 납부 상태와 납부일을 확인한다.
- 전체 부과액, 납부액과 미납액을 요약해서 확인한다.

#### 운영진 기능

- 회비 항목을 등록·수정·마감한다.
- 회비 대상 멤버를 전체 또는 일부로 지정한다.
- 개별 또는 일괄로 납부·미납 상태를 처리한다.
- 항목별 대상 인원, 납부 인원, 미납 인원과 수납액을 확인한다.
- 납부 상태 변경자와 변경 이력을 확인한다.

#### 정책

- 1차 범위는 계좌이체 후 운영진이 수기로 납부 여부를 확인하는 방식으로 한다.
- 온라인 결제, 자동 입금 확인, 부분 납부, 환불과 영수증은 제외한다.
- 회비 항목 생성 당시 대상자를 확정해 이후 가입자가 과거 회비에 자동 포함되지 않게 한다.
- 회비 항목은 납부 이력이 있으면 물리 삭제하지 않고 마감 또는 취소 상태로 변경한다.

#### 논의 필요

- 팀장에게 소속 팀 회비 현황 조회 권한을 줄 것인가?
- 운영진 중 회비 담당자만 전체 금액을 볼 수 있도록 분리할 것인가?
- 납부 증빙 이미지를 받을 것인가?

### F-11. 멤버·권한

#### 목적

운영진이 동아리 멤버의 등록 상태, 학교 인증 연결, 팀, 기수와 권한을 관리한다.

#### 멤버 등록

- 운영진은 학번, 이름, 팀과 기수를 입력해 멤버를 등록한다.
- 신규 멤버의 최초 권한은 항상 일반 부원이며, 팀장·운영진 승격은 등록 후 별도 권한 변경과 이력 기록으로 처리한다.
- 등록 직후 상태는 `SSO 연결 대기`로 설정한다.
- 해당 학번으로 학교 인증에 성공하고 등록 정보가 일치하면 서비스 계정과 멤버를 연결하고 `활성` 상태로 전환한다.
- 온보딩 도입 전에는 별도의 소속 확인·필수 동의 완료를 활성화 조건으로 사용하지 않는다.
- 동일 동아리에서 같은 학번을 중복 등록할 수 없다.
- 한 멤버는 동시에 하나의 팀에만 소속될 수 있다.
- 학교 인증에서 확인한 이름과 등록 이름이 다르면 운영진 확인 대상으로 표시한다.

#### 멤버 상태 후보

- `SSO 연결 대기`
- `활성`
- `활동 중지`
- `탈퇴`
- `등록 취소`

#### 상태 전이

- 운영진은 `SSO 연결 대기 → 등록 취소`, `활성 → 활동 중지 또는 탈퇴`, `활동 중지 → 활성 또는 탈퇴`만 처리할 수 있다.
- `SSO 연결 대기 → 활성`은 학교 SSO 대조 성공 흐름에서만 처리한다.
- `탈퇴`와 `등록 취소`는 1차 범위에서 다른 상태로 되돌리지 않는다.

#### 관리 기능

- 이름, 학번, 팀, 기수, 권한, 상태와 SSO 연결 여부를 조회한다.
- 팀과 기수를 변경한다.
- 팀 또는 기수를 변경하면 현재값을 새 값 하나로 교체하고 변경 이력을 남긴다.
- 일반 부원, 팀장, 운영진 권한을 변경한다.
- 멤버를 활동 중지 또는 탈퇴 처리한다.
- 팀, 기수, 권한과 상태 변경 이력을 확인한다.

#### 보호 정책

- 탈퇴 멤버가 작성한 활동 기록과 회비 이력은 유지한다.
- 멤버는 물리 삭제보다 상태 변경을 기본으로 한다.
- 마지막 운영진의 권한 해제를 금지한다.
- 운영진 본인의 권한 해제는 추가 확인 또는 다른 운영진 승인을 요구한다.
- 멤버 등록과 팀·기수·권한·상태 변경은 인증된 활성 운영진만 실행하며, 처리자 식별자는 요청 본문이 아니라 로그인 세션에서 가져온다.
- 팀장 권한은 특정 팀 범위와 함께 관리한다.
- 주 팀과 보조 팀 개념은 두지 않는다.

#### 상태·직책 확정

- 졸업·휴학·군휴학은 학교 학적 상태로 관리하고 동아리 멤버 상태 코드를 세분화하지 않는다.
- 회장·총무 같은 직책은 시스템 권한과 분리하며, 1차 구현에서는 별도 직책 컬럼을 만들지 않는다.

### F-12. 공연 제작·관람 운영

#### 목적

학기별 공연 제작 프로젝트를 중심으로 팀별 제작 진행, 소품·장비, 체크리스트, 외부 공연 홍보, 공연 회차, 관람 신청과 당일 입장을 연결한다.

#### 확정 정책

- 공연 제작 프로젝트는 학기당 하나를 운영한다.
- 하나의 프로젝트에서 여러 공연 회차가 파생된다.
- 제작 업무와 체크리스트의 담당 단위는 개인이 아닌 팀이다.
- 일반 부원도 소속 팀의 제작 업무를 생성하고 상태를 변경할 수 있다.
- 팀장은 소속 팀 업무와 체크리스트를 관리한다.
- 운영진은 전체 팀과 공연 운영 정보를 관리한다.
- 외부 공연 홍보 페이지에는 포스터, 작품 소개, 캐스팅 보드, 회차별 캐스팅, 제작진, 관람 안내, 공연 관련 공시와 관람 신청 동선을 제공한다.
- 내부 멤버 정보와 외부 공개 출연자 프로필을 분리하고 이름·사진·소개 공개 동의를 관리한다.
- 외부 관람객은 신청 내역을 조회하고 취소 가능 기한 전까지 직접 취소할 수 있다.
- 공연 당일에는 예약 단위 QR을 스캔하고 실제 입장 좌석을 선택해 처리한다.
- QR에는 개인정보를 담지 않고 추측하기 어려운 입장 토큰만 사용한다.
- 좌석 배치 생성과 재사용 정책은 별도 기획 완료 전까지 보류한다.

#### 상세 기획

팀별 진행 상태, 소품·장비, 체크리스트, 외부 홍보 페이지, 캐스팅 보드, 신청 조회·취소와 QR 입장 흐름은 [`performance-operations-plan.md`](performance-operations-plan.md)를 따른다.

## 5. 폐기 기능 정리

### 5.1 일정 조율

다음 범위를 제거 대상으로 본다.

- 사이드바와 홈의 일정 조율 진입점
- 일정 조율 화면과 화면 전용 JavaScript
- 개발용 라우팅과 역할 설정
- 일정 조율 관련 테스트와 샘플 데이터
- 스타일 가이드의 일정 조율 전용 예제
- 기능 정의서와 백엔드 설계의 조율 도메인, URL과 테이블 초안
- 캘린더의 일정 조율 원본 참조

### 5.2 커뮤니티 게시판

다음 범위를 제거 대상으로 본다.

- 사이드바와 홈의 게시판 진입점 및 최근 게시글 요약
- 게시판 화면과 화면 전용 JavaScript
- 개발용 라우팅과 역할 설정
- 게시판 관련 테스트와 샘플 데이터
- 게시글, 댓글, 좋아요 관련 백엔드 초안

게시판은 영구 폐기가 아니라 1차 범위에서 제외한 기능이다. 추후 추가할 때 기존 목업을 그대로 복구하지 않고 요구사항을 새로 작성한다.

새로 추가하는 공시·공지 게시판은 기존 커뮤니티 게시판 코드를 유지하는 근거가 아니다. 공시는 외부 공식 안내, 공지는 내부 전달 기능이며 댓글·좋아요·일반 글 작성 없이 각각 별도 구현한다.

## 7. 공통 운영·보안 요구사항

- 모든 내부 기능은 로그인 세션과 서버 권한 검증을 거친다.
- 학교 비밀번호, 학교 세션 쿠키, 회비 관련 민감정보를 로그에 기록하지 않는다.
- 사용자 입력과 파일 업로드를 서버에서 다시 검증한다.
- 모든 업무 파일은 `FILE_STORAGE_ROOT` 영구 볼륨(운영 기본값 `/data/bandi`)에 저장하고 DB에는 상대 저장 키와 검증 메타데이터만 기록한다.
- 내부 자료와 활동 인증 사진은 `private/`에 저장하고, 서버 권한 확인 후 Spring Boot가 직접 전송한다.
- 외부 공개 파일은 승인된 공시만 `public/`에 별도 복사한다. 비공개 파일의 같은 키를 공개 전환하지 않는다.
- 원본 파일명과 서버 생성 저장 키를 분리하고 키에 개인정보를 포함하지 않는다.
- 저장 경로는 정규화해 scope 루트 이탈을 차단하며, 파일 경로와 파일 내용은 정적 서버로 직접 노출하지 않는다.
- 멤버, 활동 기록, 회비처럼 이력 보존이 필요한 데이터는 소프트 삭제 또는 상태 변경을 사용한다.
- 운영진의 권한 변경, 회비 처리와 기록 승인 작업은 감사 이력을 남긴다.
- 개인정보는 기능 수행에 필요한 최소 항목만 수집하고 보존 기간을 정한다.
- 학교 인증 시스템 장애가 동아리 데이터 손실로 이어지지 않도록 인증과 업무 데이터를 분리한다.

온보딩 템플릿·진행·동의·정정·후속 확인 데이터는 1차 핵심 데이터에서 제외한다. 후속 스키마는 [`member-onboarding-plan.md`](member-onboarding-plan.md)와 [`database-schema.md`](database-schema.md)의 후속 설계 절을 기준으로 다시 승인한다.

## 8. 1차 구현 순서

구현은 아래 단계를 앞에서부터 진행한다. 첫 개발 작업은 `team`·`cohort`·`member`와 변경 이력의 모델·마이그레이션·테스트이며, 온보딩 테이블을 함께 만들지 않는다. 각 기능은 이슈 1개, 브랜치 1개, PR 1개 원칙을 지킨다.

### 1단계: 사용자 기반

- 제공된 Python PoC 기반 학교 인증 어댑터 설계와 재학생 허용 정책
- 운영진의 멤버 사전 등록
- 최초 로그인 시 학번 기반 멤버 연결
- 팀, 기수와 권한 관리

### 2단계: 동아리 운영 핵심

- 통합 캘린더
- 팀별 활동 기록과 인증 사진
- 공시 게시판
- 공지·자료실과 공지 읽음 확인
- 행사와 실제 출석 관리
- 회비 수기 관리
- 역할별 홈 요약

### 3단계: 운영 효율화

- 학기별 공연 제작 프로젝트와 팀별 진행 상태
- 소품·장비와 공연 체크리스트
- 외부 공연 홍보 페이지, 캐스팅 보드와 제작진
- 회차별 캐스팅, 관람 안내와 공연 공시 연동
- 관람 신청 조회·취소와 QR 입장 관리
- 수동 등록의 운영 비용이 큰 경우에만 Google Sheets 읽기 연동 재평가
- 활동 인증 사진 자동 판독 필요성 검토
- 알림 기능 검토

### 후속 단계: 신입 부원 온보딩

- 1차 구현과 운영 검증이 끝난 뒤 별도 이슈·브랜치·마이그레이션으로 진행한다.
- 필수 동의 문구, 일반 기능 개방 시점, 팀별 콘텐츠 책임자와 완료 기한을 먼저 확정한다.
- 기존 멤버·SSO 흐름을 깨지 않도록 선택 적용과 기존 멤버 이관 정책을 함께 설계한다.

## 9. 우선 확정이 필요한 질문

1. 일반 부원이 생성한 제작 업무의 수정·삭제 범위를 정한다.
2. 관람 신청 취소 마감과 좌석 일부 취소 허용 여부를 정한다.
3. 좌석 배치 정책은 별도 기획 결과를 반영한다.
4. 공개 출연자 프로필의 동의 절차와 공연 종료 후 보존 정책을 정한다.
5. 공연별 시각적 변형과 강조색 허용 범위를 정한다.
6. 홈 화면에서 역할별로 가장 먼저 보여야 할 지표는 무엇인가?
7. 행사 출석의 본인 체크인 허용 여부와 현장 확인 방식을 정한다.

온보딩 관련 미확정 사항은 현재 구현의 차단 조건이 아니며 [`member-onboarding-plan.md`](member-onboarding-plan.md)에서 별도로 관리한다.

## 10. 구현 기준과 선행 조건

- 이 문서는 1차 구현의 기능 정본이다. 이슈와 구현이 충돌하면 변경 승인 없이 이 문서를 벗어나지 않는다.
- 일정 조율과 커뮤니티 관련 실제 코드 삭제는 별도 작업으로 수행하고 빌드·화면 회귀 검증을 거친다.
- 학교 계정 인증은 컨벤션 18장의 학교 SSO·세션 정책을 따르며 로컬 폼 로그인 전제를 사용하지 않는다.
- 권한은 컨벤션 18.2와 동일한 `ADMIN`, `LEADER`, `MEMBER`만 사용한다.
- DB `CHECK`와 generated column은 컨벤션 11.3의 확정 규칙을 따른다.
- 온보딩은 현재 구현 범위가 아니며 관련 화면·API·테이블을 다른 기능에 끼워 넣지 않는다.

## 11. 목업 운영·UX 검토

현재 목업과 확정 기능의 차이, 화면별 변경안, 모달과 전용 작성 페이지의 기준, 푸터 정책과 적용 순서는 [`mockup-operations-review.md`](mockup-operations-review.md)에서 관리한다.

기능 구현 전에 해당 문서의 P0 항목을 먼저 반영해 로그인, 메뉴 구조와 모바일 레이아웃을 확정한다. 기능 정의와 목업이 충돌하면 이 기능 정의서를 우선한다.

## 12. 데이터베이스 스키마

확정 기능을 기준으로 한 테이블, 관계, 제약, 인덱스, 트랜잭션과 개인정보 저장 원칙은 [`database-schema.md`](database-schema.md)에서 관리한다.

해당 문서의 1차 마이그레이션 순서를 구현 기준으로 사용한다. 좌석 배치와 온보딩처럼 제외·미확정인 정책은 확정 후 별도 마이그레이션으로 추가한다.
