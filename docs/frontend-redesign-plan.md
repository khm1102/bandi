# bandi 프론트엔드 재설계 계획

> 작성 기준일: 2026-07-20
> 목적: 전체 JSP 화면을 유형별로 분류하고, 토스 제품 원칙(다음 행동 우선·한 화면 한 결정·점진 공개·모바일 우선) 기반 재설계의 단계와 필요 API를 관리한다.
> 공통 셸과 공연 운영 3화면을 출발점으로 삼아 전체 화면을 순차 구현한다. 필요한 UX를 현재 API가 지원하지 않으면 정본·보안·권한 경계를 확인한 뒤 테스트부터 백엔드 계약을 보완한다.
> 화면별 상세 spec: `.ui-craft/spec.md` · 디자인 정본: `docs/design-guide.md`

## 1. 화면 유형 분류

| 유형 | 정의 | 해당 화면 |
|---|---|---|
| 업무 홈 | 역할별 "지금 할 일" 요약 | 대시보드 |
| 목록·탐색 | 조회·필터·상세 진입 중심 | 캘린더, 공지·자료실, 활동 기록, 팀별 제작, 소품·장비, 체크리스트, 행사·출석, 회비, 멤버, 공시 관리 목록, 관람 신청 관리 |
| 설정·작성 | 저장이 목적인 폼·구성 화면 | 공연 운영 설정, 공연 콘텐츠, 공시 작성 |
| 현장 운영 | 현장에서 반복 처리하는 조작 화면 | 공연 당일 입장, (행사 출석 현장 처리) |
| 외부 공개 | 비로그인 사용자 대상 | 공개 공연 페이지, 공시 목록·상세, 관람 신청, 신청 조회·취소 |
| 인증·오류 | 세션 진입·이탈 | 로그인, 403/404/500 |

## 3. 마이그레이션 단계

1. **1단계**: 토큰(버건디 전환)·그룹형 사이드바·modal/sheet/reduced-motion + `/performance-management`, `/reservations`, `/showops` — 구현 완료
2. **2단계**: 매일 쓰는 화면 — 대시보드, 공지·자료실, 체크리스트, 행사·출석 — 구현 완료
3. **3단계**: 운영 목록 — 캘린더, 활동 기록, 팀별 제작, 회비, 멤버 — 구현 완료
4. **4단계**: 저빈도 관리 — 소품·장비, 공시 관리(목록·에디터), 공연 콘텐츠 — 구현 완료
5. **5단계**: 외부 공개·인증·오류 — 구현 완료
6. **6단계**: 전체 데이터 정합성·보안·MinIO·상태 전이·반응형·키보드 회귀 및 출시 게이트 — 자동 검증 완료, 인증 세션 시각 확인 필요

전역 토큰·사이드바 변경으로 2~5단계 화면에도 색·내비 변화가 즉시 적용된다. 대비·가독성이 깨지는 곳만 최소 호환 수정하고 구조 재설계는 각 단계에서 한다.

### 3.1 6단계 검증 기록

- `./gradlew build`: 전체 977개 테스트 통과
- Jasper `JspC`: 전체 JSP·태그 파일 컴파일 오류 0건
- 전체 JavaScript: `node --check` 문법 오류 0건
- 공개 화면 `/login`, `/notices`, `/reserve`, 404: 320·375·768·1440px에서 가로 넘침, 중복 ID, 무라벨 입력, 44px 미만 터치 대상 없음
- 공개 화면 브라우저 콘솔: 의도한 404 리소스 응답 외 JavaScript 예외 없음
- 공개 공연·공시의 존재하지 않는 상세: HTML 404, 같은 API 요청: JSON 404로 계약 분리 확인
- 인증이 필요한 내부 화면은 실제 로그인 세션에서의 최종 시각·키보드 확인이 남아 있다. 테스트 비밀번호를 읽거나 인증을 우회하지 않는다.

## 4. 필요 API와 백엔드 보완 후보

> 이 섹션의 API는 제안 상태에서 시작한다. 정본과 권한 정책이 확정된 항목만 model·Service TDD와 Controller·Mapper 검증을 거쳐 구현하며, 보류 정책은 가짜 데이터나 임시 endpoint로 우회하지 않는다.

### 4.1 좌석 배치 생성·재사용

- **필요한 사용자 경험**: 공연 운영 설정의 준비 체크리스트에서 "좌석 준비" 완료 여부를 보여주고, 신청 관리에서 "좌석 준비가 필요해요" 상태를 안내한다.
- **현재 API로 불가능한 이유**: 좌석 배치 정책 자체가 보류 상태라 관리자용 좌석 생성·조회 API가 없다.
- **제안 endpoint**: GET `/api/performance-management/rounds/{roundId}/seats/summary`
- **request**: path `roundId`
- **response 최소 필드**: `{ totalSeatCount: number, hasLayout: boolean }`
- **빈 상태·오류 코드**: 좌석 미구성 시 `hasLayout: false`(404 아님), 404 = 회차 없음, 403 = 권한 없음
- **우선순위**: 좌석 정책 확정 후 최우선

### 4.2 목록 total / hasNext

- **필요한 사용자 경험**: 신청 관리 "더 보기"에서 전체 건수와 남은 페이지를 알려주고, CSV 진행률을 정확히 표시한다.
- **현재 API로 불가능한 이유**: `GET /rounds/{roundId}/reservations`가 배열만 반환하고 total·hasNext가 없다. 현재는 응답 < limit으로 마지막을 추정한다.
- **제안 endpoint**: 기존 endpoint 응답 확장 `{ items: [...], total: number, hasNext: boolean }` 또는 `X-Total-Count` 헤더
- **request**: 기존과 동일 (`projectId`, `status`, `offset`, `limit`)
- **response 최소 필드**: `total`, `hasNext`
- **빈 상태·오류 코드**: 0건이면 `total: 0, items: []`
- **우선순위**: 중간

### 4.3 관람 신청 서버 검색

- **필요한 사용자 경험**: 신청 관리에서 이름·신청번호·연락처로 전체 신청을 검색한다.
- **현재 API로 불가능한 이유**: 목록 API에 검색 파라미터가 없다. 클라이언트 검색은 로드된 페이지만 대상이라 전체 검색처럼 보이면 안 되므로 검색창을 만들지 않았다.
- **제안 endpoint**: GET `/api/reservation-management/rounds/{roundId}/reservations?keyword=`
- **request**: `keyword` (이름 부분 일치 또는 신청번호 정확 일치), 기존 페이징 파라미터 유지
- **response 최소 필드**: 기존 목록 응답과 동일
- **빈 상태·오류 코드**: 결과 없음 = 빈 배열, 400 = keyword 형식 오류
- **우선순위**: 높음 (현장 문의 대응)

### 4.4 파일 업로드 세션 / 고아 파일 정리

- **필요한 사용자 경험**: 외부 공연 페이지 저장에서 이미지 업로드 후 본문 저장이 실패해도 저장소에 쓰이지 않는 파일이 남지 않는다.
- **현재 API로 불가능한 이유**: 업로드(`POST /api/files/private` → `public-promotions`)와 본문 저장이 별도 호출이라, 본문 저장 실패 시 승격된 파일이 고아로 남는다. 클라이언트가 삭제 API로 보상할 수단도 없다.
- **제안 endpoint**: ① DELETE `/api/files/{fileId}` (미참조 파일 한정) 또는 ② 서버 배치의 미참조 파일 TTL 정리
- **request**: ①의 경우 path `fileId`
- **response 최소 필드**: 204
- **빈 상태·오류 코드**: 409 = 이미 참조 중, 404 = 없음
- **우선순위**: 낮음 (저장 실패 빈도 낮음, 저장 용량 문제 시 상향)

### 4.5 세션 만료 후 원래 화면 복귀

- **필요한 사용자 경험**: 작성 중 401이 나도 재로그인 후 원래 화면(가능하면 작성 상태)으로 돌아온다.
- **현재 API로 불가능한 이유**: SSO 로그인 흐름에 returnTo 파라미터 계약이 없다. 프론트는 현재 "재로그인 필요 + 입력은 이 화면에 남아 있음"만 안내한다.
- **제안 endpoint**: GET `/login?returnTo={상대경로}` 허용 + 로그인 성공 시 검증된 내부 경로로 리다이렉트
- **request**: `returnTo` (내부 상대경로만 허용, 화이트리스트 검증)
- **response 최소 필드**: 302 Location
- **빈 상태·오류 코드**: 검증 실패 시 기본 홈으로
- **우선순위**: 중간
- **비고**: open redirect 방지 검증이 백엔드 범위라 프론트 단독 구현 금지.

### 4.6 공연 당일 최근 입장 처리 이력

- **필요한 사용자 경험**: 입장 화면에서 방금 처리한 내역(좌석·시각)을 목록으로 확인하고 잘못 처리를 바로 찾는다.
- **현재 API로 불가능한 이유**: 회차별 입장 처리 이력 조회 API가 없다. 클라이언트 메모리로 흉내 내면 새로고침·기기 간 불일치가 생기므로 만들지 않았다.
- **제안 endpoint**: GET `/api/reservation-management/rounds/{roundId}/entry/check-ins?limit=20`
- **request**: `limit`(기본 20), `offset`
- **response 최소 필드**: `[{ reservationNo, seatLabel, checkedInDttm, cancelled: boolean }]` (이름은 마스킹 또는 제외 — 개인정보 최소화)
- **빈 상태·오류 코드**: 빈 배열, 403 = 권한 없음
- **우선순위**: 중간

### 4.7 공시 연결 목록 페이징

- **필요한 사용자 경험**: 연결 가능한 공시가 100건을 넘어도 모두 선택할 수 있다.
- **현재 API로 불가능한 이유**: `GET /api/admin/public-notices`를 `pageSize=100`으로 두 번(PUBLISHED·SCHEDULED) 호출하는 구조라 100건 초과분이 잘린다.
- **제안 endpoint**: 기존 endpoint에 `page`/`offset` 파라미터와 total 추가
- **request**: `status`, `page`, `pageSize`
- **response 최소 필드**: `items`, `total`
- **빈 상태·오류 코드**: 빈 배열
- **우선순위**: 낮음 (공시 100건 초과는 당분간 비현실적)

### 4.8 입장 조회 오류의 기계 판별 코드

- **필요한 사용자 경험**: "다른 회차의 QR" / "일치하지 않는 QR" / "취소된 신청"을 각각 다른 안내와 다음 행동으로 보여준다.
- **현재 API로 불가능한 이유**: entry/lookup 실패 응답의 `code`가 상황별로 세분되어 있지 않으면 메시지 문자열로만 구분해야 한다.
- **제안 endpoint**: 기존 오류 응답의 `code` 세분화 — `ENTRY_TOKEN_NOT_FOUND`, `ENTRY_ROUND_MISMATCH`, `RESERVATION_CANCELLED`
- **request**: 변경 없음
- **response 최소 필드**: `code`, `message`
- **빈 상태·오류 코드**: 상기 코드
- **우선순위**: 중간
