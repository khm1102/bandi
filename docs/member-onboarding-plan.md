# bandi 신입 부원 온보딩 후속 기획

> 문서 상태: 설계 동결·1차 구현 제외·후속 작업에서 재검토
> 작성 기준일: 2026-07-18
> 관련 문서: `feature-spec.md`

> 구현 경계: 현재 문서는 후속 온보딩 기능의 설계 기록이다. 현재 제공하는 `/onboarding`은
> 동아리 기본 안내와 사이트 튜토리얼만 담는 정적 화면이며, 이 문서의 온보딩 기능으로 보지
> 않는다. 1차 구현에서는 온보딩 템플릿, 배정, 단계 진행, 정정 요청과 후속 확인을 만들지 않는다.

> 재개 조건: 1차 멤버·SSO 운영 검증 후 필수 동의 문구, 일반 기능 개방 시점, 팀별 콘텐츠 책임자, 기존 멤버 적용 방식과 완료 기한을 확정하고 별도 이슈·브랜치·마이그레이션으로 시작한다.

## 1. 목적

신입 부원이 합격 후 학교 계정으로 bandi에 처음 접속하고, 본인의 소속을 확인한 뒤 동아리 공통 규칙과 팀별 활동 방식을 이해해 실제 활동을 시작할 수 있도록 돕는다.

온보딩은 회원가입 화면 하나가 아니라 다음 세 과정을 연결한다.

1. 운영진의 합격자 사전 등록
2. 첫 학교 계정 인증과 멤버 연결
3. 동아리·팀 안내와 초기 할 일 완료

## 2. 온보딩 원칙

- 학교 인증 성공과 동아리 멤버 활성화를 분리한다.
- 합격자로 사전 등록된 학번만 내부 멤버로 연결한다.
- 학교 비밀번호는 저장하지 않는다.
- 신입 부원에게 처음부터 모든 정보를 보여주지 않고 단계별로 안내한다.
- 필수 동의와 정보 확인 외의 안내 단계는 나중에 이어서 완료할 수 있게 한다.
- 운영진은 멤버별 진행 상태와 중단 지점을 확인할 수 있어야 한다.
- 공통 안내와 팀별 안내를 분리하고, 운영진이 기수·팀별 템플릿을 편집할 수 있게 한다.
- 문서 확인만으로 끝내지 않고 첫 번째 실제 활동과 후속 체크인을 온보딩에 연결한다.
- 신규 멤버가 질문할 담당자와 도움을 받을 경로를 각 템플릿에 표시한다.
- 동의 이력과 소속 변경은 추적하되, 불필요한 행동 분석은 수집하지 않는다.

### 2.1 콘텐츠 제공 원칙

- 첫 화면에 모든 규칙과 문서를 몰아넣지 않고 짧은 카드·단계·체크리스트로 나눈다.
- 모든 멤버에게 같은 내용을 강제하지 않고 공통 단계와 팀별 단계를 구분한다.
- 각 단계는 `왜 필요한지`, `무엇을 하면 되는지`, `누구에게 물어볼지`를 함께 보여준다.
- 필수 단계와 선택 안내를 시각적으로 구분한다.
- 마지막에는 완료 상태, 다음 일정과 첫 활동을 요약해 온보딩의 끝을 명확히 한다.

## 3. 사용자와 담당자

| 역할 | 온보딩 책임 |
|---|---|
| 신입 부원 | 학교 인증, 본인 정보 확인, 필수 동의, 공통·팀 안내 확인, 초기 할 일 수행 |
| 팀장 | 소속 팀 안내 제공, 팀 채널과 첫 일정 안내, 팀별 초기 할 일 확인 |
| 운영진 | 합격자 사전 등록, 공통 안내 관리, 진행 현황 확인, 정보 불일치와 예외 처리 |

## 4. 전체 여정

| 단계 | 주체 | 주요 행동 | 완료 기준 |
|---|---|---|---|
| 1. 선발 완료 | 운영진 | Google Sheets에서 합격자를 확정한다. | 합격자와 배정 정보가 확정됨 |
| 2. 사전 등록 | 운영진 | 학번, 이름, 기수와 팀을 bandi에 입력한다. | 멤버가 `SSO 연결 대기` 상태로 생성됨 |
| 3. 접속 안내 | 운영진 | 학교 계정 로그인 주소, 첫 진행 순서와 문의 담당자를 전달한다. | 신입 부원이 접속 방법과 도움 요청 경로를 전달받음 |
| 4. 첫 학교 인증 | 신입 부원 | 학교 계정으로 인증한다. | 인증 학번과 사전 등록 학번이 일치함 |
| 5. 정보 확인 | 신입 부원 | 이름, 기수, 팀과 역할을 확인한다. | 정보 확인 또는 정정 요청이 제출됨 |
| 6. 필수 동의 | 신입 부원 | 개인정보 처리와 동아리 운영 규칙에 동의한다. | 필수 동의 버전과 시각이 기록됨 |
| 7. 공통 안내 | 신입 부원 | 동아리 소개와 서비스 사용법을 확인한다. | 필수 공통 안내를 모두 확인함 |
| 8. 팀 안내 | 신입 부원·팀장 | 팀 역할, 채널, 일정과 첫 할 일을 확인한다. | 팀별 필수 항목을 완료함 |
| 9. 첫 활동 | 신입 부원·팀장 | 첫 팀 일정, 자료 확인 또는 첫 업무를 수행한다. | 실제 활동 연결 항목이 완료됨 |
| 10. 후속 확인 | 팀장·운영진 | 1주·1개월 시점에 적응 상태와 질문을 확인한다. | 후속 확인 기록이 남고 지원 필요 여부가 정리됨 |
| 11. 온보딩 완료 | 시스템·운영진 | 필수 단계와 첫 활동을 완료하고 홈으로 이동시킨다. | 온보딩 상태가 `완료`로 변경됨 |

## 5. 신입 부원 화면 흐름

### 5.1 첫 진입

- 학교 인증에 성공한 뒤 사전 등록된 멤버와 일치하면 온보딩 시작 화면으로 이동한다.
- 온보딩을 완료하지 않은 사용자가 다시 로그인하면 마지막 미완료 단계부터 이어서 진행한다.
- 사전 등록 정보가 없으면 내부 기능으로 진입시키지 않고 운영진 문의 방법을 안내한다.

### 5.2 1단계: 소속 정보 확인

다음 정보를 표시한다.

- 이름
- 마스킹된 학번
- 가입 기수
- 소속 팀
- 기본 역할

사용자는 `정보가 맞아요` 또는 `수정이 필요해요`를 선택한다.

수정 요청이 발생하면 사용자가 직접 팀과 기수를 바꾸지 않고, 운영진이 확인해 수정한다. 확인 전까지는 온보딩 상태를 `확인 필요`로 유지한다.

### 5.3 2단계: 필수 동의

필수 동의 후보는 다음과 같다.

- bandi 개인정보 수집·이용 안내
- 동아리 운영 규칙 확인
- 활동 인증 사진 업로드와 이용 범위 확인

각 동의에는 문서 버전, 동의 여부와 동의 시각을 기록한다. 선택 동의가 추가되면 필수 동의와 구분한다.

### 5.4 3단계: 동아리 공통 안내

공통 안내 내용 후보는 다음과 같다.

- 동아리 소개와 활동 목적
- 조직 구성과 팀별 역할
- 운영진과 문의 방법
- 주요 연간 일정과 정기 활동
- 공시 확인 방법
- 캘린더 이용 방법
- 공지와 자료 확인 방법
- 네이비즘 인증 사진을 포함한 활동 기록 작성 방법
- 기본 운영 규칙과 금지 사항

긴 설명 한 페이지보다 짧은 카드 또는 단계별 문서로 제공한다. 각 항목에는 `확인했어요` 처리를 제공한다.

### 5.5 4단계: 팀별 안내

팀별 안내 내용 후보는 다음과 같다.

- 팀 소개와 담당 업무
- 팀장과 연락 방법
- 팀에서 사용하는 외부 채널 링크
- 정기 모임 시간과 장소
- 현재 진행 중인 업무
- 첫 모임 또는 첫 일정
- 팀별 자료와 활동 기록 작성 규칙

외부 채널의 초대 토큰이나 비밀번호는 bandi에 직접 노출하지 않고, 만료 가능한 초대 링크 또는 운영진 안내를 사용한다.

### 5.6 5단계: 첫 할 일 체크리스트

1차 체크리스트 예시는 다음과 같다.

- 내 팀과 기수 확인
- 필수 운영 규칙 확인
- 중요 공시 읽기
- 팀 연락 채널 참여
- 첫 팀 일정 확인
- 가까운 일정 확인
- 활동 인증 기록 작성 방법 확인

체크리스트는 실제 기능 완료와 자동 연결할 수 있는 항목과 단순 확인 항목을 구분한다.

예를 들어 공지 읽기, 자료 확인, 첫 활동 기록 확인은 실제 기능 완료와 연결할 수 있다. 외부 채널 참여나 팀원 소개는 사용자의 확인 또는 팀장의 확인으로 완료 처리한다.

### 5.7 완료 화면

- 온보딩 완료를 안내한다.
- 소속 팀, 팀장과 다음 일정을 요약한다.
- 홈으로 이동하는 버튼을 제공한다.
- 미완료 선택 항목이 있으면 홈에서 다시 접근할 수 있게 한다.

### 5.8 후속 확인

- 온보딩 완료 후에도 홈에서 `첫 주 확인`, `첫 달 확인` 항목을 다시 열 수 있다.
- 팀장 또는 운영진은 신입 부원의 첫 활동 여부와 질문·지원 필요 여부를 기록한다.
- 후속 확인은 평가나 감시 목적이 아니라 역할 이해와 소속감 형성을 위한 지원 절차로 운영한다.
- 버디 또는 선배 멤버 연결은 필수 기능이 아니라 운영진이 필요할 때 지정하는 선택 기능으로 둔다.

## 6. 운영진 관리 기능

### 6.1 사전 등록

- 학번, 이름, 기수, 팀과 기본 역할을 입력한다.
- 등록 상태는 `SSO 연결 대기`로 시작한다.
- 동일 학번의 활성 또는 등록 대기 멤버가 있으면 중복 등록을 막는다.
- 잘못 등록한 멤버는 SSO 연결 전에 취소할 수 있다.

### 6.2 진행 현황

운영진은 다음 상태별 인원과 명단을 확인한다.

- SSO 연결 대기
- 온보딩 진행 중
- 정보 확인 필요
- 온보딩 완료
- 등록 취소

멤버별 마지막 완료 단계와 마지막 진행 시각을 확인한다. 학교 비밀번호, 학교 세션과 원본 인증 응답은 표시하지 않는다.

### 6.3 예외 처리

- 사전 등록 이름과 학교 인증 이름이 다르면 학번 일치 여부를 우선 확인하고 운영진 검토 대상으로 표시한다.
- 팀이나 기수가 잘못된 경우 운영진이 수정한 뒤 해당 단계를 다시 확인하게 한다.
- 다른 멤버에 잘못 연결된 경우 일반 수정 기능으로 덮어쓰지 않고 연결 해제 이력을 남긴다.
- 중도 탈퇴 또는 합격 취소자는 등록 취소 처리하고 내부 접근을 차단한다.
- 온보딩 진행이 장기간 멈춘 멤버는 운영진이 안내할 수 있도록 상태를 필터링한다.

#### 진행 중 팀 변경

- 운영진이 팀을 변경하면 공통 단계와 이전 팀에서 이미 완료·면제된 결과는 이력으로 유지한다.
- 이전 팀의 미완료 단계는 더 이상 진행하지 않도록 종료하고, 새 팀의 미완료 단계를 진행 목록에 편입한다.
- 과거에 소속됐던 팀으로 돌아온 경우 이미 완료한 단계는 반복시키지 않고, 당시 미완료였던 단계만 다시 연다.
- 새 팀의 필수 단계가 남아 있으면 완료된 온보딩도 `진행 중`으로 다시 열고 멤버에게 변경 사실과 남은 단계를 알린다.
- 완료 여부는 공통 단계와 현재 팀의 필수 단계만으로 다시 계산한다.

### 6.4 안내 콘텐츠 관리

운영진은 기본 템플릿을 복제해 기수별·팀별 온보딩 템플릿을 만들고 게시한다.

#### 템플릿 단계 유형

- 안내문: 동아리·팀 소개와 운영 방식
- 확인 항목: `확인했어요` 처리
- 필수 동의: 개인정보와 운영 규칙
- 체크리스트: 첫 일정·자료·업무 확인
- 링크: 외부 채널 또는 추가 문서
- 입력 항목: 자기소개나 필요한 운영 정보
- 실제 기능 연결: 공지 읽기, 자료 확인, 첫 활동 기록 확인

#### 운영진 편집 항목

- 단계 제목과 본문
- 단계 유형
- 필수 여부
- 표시 순서
- 적용 팀과 기수
- 완료 기한
- 문의 담당자
- 연결할 기능 또는 링크

템플릿은 `초안 → 게시 → 보관` 상태로 관리한다. 게시할 때 버전을 발행하고, 멤버에게는 배정 시점의 게시 버전을 적용한다. 이미 진행 중인 멤버에게 게시 후 수정사항을 예고 없이 적용하지 않는다.

팀별 안내의 최종 게시 권한은 운영진이 갖고, 팀장은 운영진이 허용한 범위에서 팀 내용을 제안하거나 수정 요청할 수 있게 하는 방향을 우선안으로 둔다.

## 7. 접근 제어 제안

### 7.1 필수 완료 전

- 학교 인증과 멤버 연결이 완료되지 않으면 내부 기능에 접근할 수 없다.
- 소속 정보 확인과 필수 동의 전에는 온보딩 화면과 로그아웃만 허용한다.
- 정보 정정 요청 상태에서는 운영진 안내와 요청 상태만 확인할 수 있다.

### 7.2 필수 완료 후

- 소속 정보 확인과 필수 동의를 마치면 내부 기능을 사용할 수 있다.
- 필수 단계를 마치면 멤버 상태를 `활성`으로 전환한다.
- 공통 안내와 팀 체크리스트가 남아 있으면 홈에 온보딩 진행 카드를 표시한다.
- 안내 확인을 모두 마치면 온보딩을 최종 완료 처리한다.
- 필수 단계와 첫 활동을 마치면 `완료`로 처리하되, 1주·1개월 후속 확인은 별도 상태로 관리한다.

이 방식은 필수 정책 확인은 보장하면서, 외부 채널 참여나 첫 일정처럼 즉시 완료하기 어려운 항목 때문에 서비스 전체가 잠기는 것을 방지한다.

## 8. 상태 정의 초안

| 상태 | 의미 |
|---|---|
| `SSO 연결 대기` | 운영진 사전 등록은 완료됐지만 첫 학교 인증 전 |
| `진행 중` | 학교 인증과 연결을 완료하고 온보딩을 진행 중 |
| `확인 필요` | 이름, 팀, 기수 또는 연결 정보에 운영진 확인이 필요함 |
| `완료` | 필수 동의와 안내 체크리스트를 완료함 |
| `등록 취소` | 합격 취소, 중복 등록 또는 운영진 판단으로 온보딩이 종료됨 |

멤버의 `활성`, `활동 중지`, `탈퇴` 상태와 온보딩 상태는 별도로 관리한다. 단, `등록 취소`의 정본은 멤버 생명주기 상태이며 온보딩의 `등록 취소`는 해당 결과를 보여 주는 배정 상태다. 운영진이 등록을 취소하면 한 트랜잭션에서 멤버를 `REGISTRATION_CANCELLED`, 온보딩 배정을 `CANCELLED`로 전환하고 내부 접근과 SSO 연결을 차단한다. 두 상태가 불일치하면 멤버 상태를 우선해 접근을 차단하고 운영진 확인 대상으로 표시한다.

## 9. 데이터 초안

| 데이터 | 주요 속성 |
|---|---|
| 온보딩 템플릿 | 이름, 적용 기수, 상태, 게시 버전, 작성·수정자 |
| 온보딩 템플릿 단계 | 템플릿 버전, 단계 유형, 제목, 설명, 필수 여부, 적용 팀, 표시 순서, 연결 기능 |
| 온보딩 배정 | 멤버, 적용 템플릿 버전, 시작 시각, 현재 단계, 상태, 완료 시각 |
| 단계 진행 | 온보딩 배정, 단계, 완료 여부, 완료 시각, 확인자 |
| 필수 동의 | 동의 문서 종류, 버전, 필수 여부, 게시 시각 |
| 멤버 동의 이력 | 멤버, 동의 문서와 버전, 동의 여부, 동의 시각 |
| 정보 정정 요청 | 멤버, 요청 항목, 요청 내용, 상태, 처리자, 처리 시각 |
| 후속 확인 | 멤버, 확인 시점, 첫 활동 여부, 지원 필요 여부, 메모, 확인자 |

템플릿 본문과 단계 정의는 게시 버전별로 보존한다. 멤버별 진행 데이터는 템플릿의 현재 내용이 아니라 배정된 게시 버전을 참조한다.

## 10. 후속 온보딩의 1차 범위

- 운영진의 합격자 수동 등록
- 첫 학교 인증과 학번 기반 멤버 연결
- 이름, 기수와 팀 확인 및 정정 요청
- 필수 개인정보·운영 규칙 동의
- 동아리 공통 안내
- 팀별 안내
- 초기 체크리스트
- 운영진의 기본 템플릿 복제·편집·게시
- 첫 활동 연결 항목
- 이어서 진행
- 운영진의 상태별 진행 현황 조회
- 1주·1개월 후속 확인 기록

## 11. 추후 확장

- 미진행 멤버 자동 알림
- 팀장 또는 온보딩 담당자 배정
- 선배·신입 버디 연결
- 활동 기록·공지 읽음·자료 확인과 자동 체크리스트 연동 고도화
- 온보딩 완료율과 평균 소요 기간 통계

## 12. 운영·개선 지표

운영진은 신입 부원의 행동을 과도하게 분석하지 않고, 온보딩이 실제 적응에 도움이 되는지 확인하는 최소 지표만 조회한다.

- 학교 인증 성공 후 멤버 연결 완료율
- 온보딩 템플릿 단계별 완료율과 중단 단계
- 첫 활동까지 걸린 기간
- 1주·1개월 후속 확인 완료율
- 지원 필요 또는 정보 정정 요청 건수
- 온보딩 종료 후 짧은 만족도·어려웠던 점 피드백

개별 페이지 체류 시간, 반복 클릭 수와 같은 행동 분석 데이터는 1차 범위에서 수집하지 않는다.

## 13. 완료 조건

- 사전 등록되지 않은 학번은 내부 멤버로 자동 생성되지 않는다.
- 사전 등록된 멤버가 첫 학교 인증 후 자신의 정보와 연결된다.
- 필수 동의 전에는 일반 내부 화면에 접근할 수 없다.
- 사용자가 중간에 종료해도 마지막 진행 상태가 보존된다.
- 정보 불일치 사용자는 운영진 확인 없이 임의로 소속을 변경할 수 없다.
- 운영진은 멤버별 진행 상태와 확인 필요 항목을 조회할 수 있다.
- 운영진은 기본 템플릿을 복제·편집하고 게시 버전을 관리할 수 있다.
- 멤버는 첫 활동 이후에도 후속 확인 안내를 받을 수 있다.
- 완료 후 사용자는 홈에서 정상적으로 동아리 기능을 사용할 수 있다.

## 14. 확정이 필요한 사항

1. 개인정보 수집·이용 외에 반드시 받아야 하는 동의 문서는 무엇인가?
2. 동아리 운영 규칙 확인을 법적 동의로 볼지 단순 확인으로 볼지 결정한다.
3. 공통 안내와 팀별 안내 중 반드시 완료해야 하는 항목을 정한다.
4. 일반 기능 접근을 필수 동의 직후 허용할지 전체 온보딩 완료 후 허용할지 결정한다.
5. 팀별 온보딩 콘텐츠 작성 책임자를 팀장과 운영진 중에서 결정한다.
6. 외부 연락 채널과 초대 링크를 bandi에 어느 범위까지 노출할지 정한다.
7. 진행이 멈춘 멤버에게 자동 알림을 보낼지 운영진이 직접 안내할지 결정한다.
8. 온보딩 완료 기한을 둘지 결정한다.
